# Automated game control

How Claude (or any script) drives the game for tests: launch it, reach the main menu, load a save, run exec functions, read the results, close it. With this, compile checks and console-command tests (see [Testing in game](development.md#testing-in-game)) run end to end with no key presses and no screenshots.

Status markers: **verified** (seen working), *unverified* (from docs, forums or the executable, not tried yet), **failed** (tried, does not work).

## Quick start

```bash
python tools/game_lock.py request --who AREA --why "slice X checks"     # the game slot: granted (token) or queued
python tools/game_lock.py wait --who AREA --timeout 540                 # when queued: until granted
python tools/build_mod.py --install-from build/AREA-<commit> --holder AREA:TOKEN   # install your prebuilt build
python tools/game.py run test --holder AREA:TOKEN                       # launch, load the test save, lock saving
python tools/game.py exec "gmpilot()" --holder AREA:TOKEN              # run exec functions, print their output
python tools/game.py quit
python tools/game_lock.py release --holder AREA:TOKEN                   # settings restored, log archived, saves compared
```

`modAutomation` is installed once by the parent (`build_mod.py --scripts tools/automation/scripts --name modAutomation --out build/automation --install --enable --parent`). The test saves are configured once per machine ([Test saves](#test-saves)). The game is one shared slot: see [The game slot](#the-game-slot).

**Verified** (game build 5.0.1044392): the whole loop above takes about 30 s: 10 s to the main menu, 12 s to load, 2 s to quit.

Requirements: Steam running; `tools/rw3d/rw3d_cli.exe` (see [rw3d_cli](#rw3d_cli)); `modAutomation` installed (a reinstall of the game deletes `<game>\mods`, and with it `modAutomation`: install it again); the test saves configured. The game window opens normally and takes the screen, but nothing needs focus or input.

## How it works

Three pieces:

| Piece | What it does |
|---|---|
| `witcher3.exe -net -debugscripts` | Started directly (no launcher). `-debugscripts` writes `LogChannel` output live to `Documents\The Witcher 3\scriptslog.txt` (rewritten at each start). `-net` opens TCP port 37001 for the script debugger protocol. |
| `modAutomation` (`tools/automation/scripts/local/modAutomation.ws`) | Test-only mod, never shipped. Logs `[Automation]` markers at the main menu, game start and end of loading, and adds exec functions to query status, load a save, close menus and quit. |
| [rw3d_cli](#rw3d_cli) (`tools/rw3d/`) | Calls exec functions in the running game over port 37001 and prints their `LogChannel` output. |

`tools/game.py` combines them: it launches the game, waits for markers in the script log, and calls the mod's exec functions through rw3d_cli.

### game.py commands

| Command | What it does |
|---|---|
| `run SAVE` | `start` then `load` |
| `start` | Checks that the installed `modGhostMode` is the one the holder installed this turn, then launches and waits for `[Automation] main menu`, closing the startup screens on the way (see [Startup screens](#startup-screens)) |
| `load SAVE` | `autoload("<file>")` of an allowed save: `test`, `slot` or a configured save's full name ([Test saves](#test-saves)); anything else is refused. Waits for `loading`, `game started`, `ready`; checks status and closes any open menu; then `gmtest_nosave()` locks saving for the session (an error if it is missing; the parent's `--parent --allow-saves` skips it) |
| `exec "CMD" ...` | Run exec functions, print their output. Fails on "Command failed to execute" (function does not exist) |
| `status` | `autostatus()`: `ingame`, `paused`, `menu` (root menu name or `none`), `loadingvideo`, `scene` |
| `resume` | `autoresume()`: close the open menu |
| `saves [-n N]` | The N newest saves (file names are reported in lower case; `autoload` matches any case) |
| `log [-n N]` | Last N script log lines |
| `quit` | `autoquit()` (`theGame.RequestExit()`), then closing the window, then killing the process |

Options: `--timeout S` per step (default 180), `--wait MS` how long rw3d_cli waits for exec output (default 500; raise it for functions that log over time). `run`, `start`, `load`, `exec` and `resume` need `--holder AREA:TOKEN` ([The game slot](#the-game-slot)). Exit code 1 on errors, timeouts or refusals, with the last log lines printed; 3 when the lock refuses because the slot is paused or the token was revoked. A failed step leaves the game running for inspection.

## The game slot

Areas are ported in parallel, one agent each ([parallel-ports.md](proposals/parallel-ports.md)), and share the one game install. `tools/game_lock.py` hands it out, one holder at a time, in request order; `game.py` and `build_mod.py`'s installs refuse to change the game without the holder's token. **Verified**: offline self-test (`game_lock.py selftest`) and real turns (install, the regression in both trees, release).

**Exclusive to the holder:** installing a build (`<game>\mods\modGhostMode`, the menu XML, `mods.settings`), the running game (`game.py run`, `start`, `load`, `exec`, `resume`), and what the game writes: `scriptslog.txt`, the settings files, the saves. `game.py quit`, `log`, `status` and `saves` stay open to everyone. Compiling is not exclusive: each `wcc_lite` run takes a short OS file lock of its own (`build_mod.py`).

**A turn:**

| Step | Command (from the main checkout's `tools/`: the only copy with rw3d_cli) |
|---|---|
| Ask | `game_lock.py request --who AREA --why TEXT`: exit 0 granted, the token printed; 2 queued (position printed); 3 paused |
| Wait | `game_lock.py wait --who AREA --timeout S`: 0 granted (token), 2 timed out (still queued: run it again), 3 paused or the token revoked. In the background when there is other work (the agent is notified when it exits); in the foreground with `--timeout 540` in a loop when idle |
| Claim | Any gated command within the **claim deadline** (default 5 minutes, `config.json`'s `claim_deadline_s`; `game_lock.py config --claim-deadline S` raises it). A grant left unclaimed is skipped: its token revoked, the next agent granted; request again |
| Play | `build_mod.py --install-from <build> --holder AREA:TOKEN`, then `game.py ... --holder AREA:TOKEN`. Every gated command renews the **lease** (20 minutes, `lease_s`) |
| End | `game.py quit`, then `game_lock.py release --holder AREA:TOKEN` |

**What the lock does:**
- **At a grant** (only with the slot free, nothing paused, the game closed, the settings baseline taken and the four settings files equal to it): backs up the saves (`robocopy <Documents>\The Witcher 3\gamesaves %USERPROFILE%\W3SaveBackup\gamesaves /E /XO`, exit codes 0-7 success; copies only, never deletes) and lists them.
- **At the release** (game closed): restores `dx12user.settings`, `input.settings`, `profile.settings` and `mods.settings` from the canonical baseline, so options a test changed (the skill tree, the experience options) never reach the next holder; archives `scriptslog.txt` into `%LOCALAPPDATA%\TGM\logs\<holder>-<time>-scriptslog.txt`; compares the saves with the grant's list (gone, new, changed) and with the backup (saves in the backup missing from the live folder) and prints and logs every difference. It restores no save: that is the owner's call.
- **The baseline** (`game_lock.py baseline --parent`): the four settings files, taken by the parent with the game closed and the owner's OK, and again only after the owner has played. It holds the owner's play settings, not test settings, so tests set every option they depend on. While the live files differ from it (the owner played), nobody is granted the game, and `watch` says so.
- **The pause** (`game_lock.py pause`, for the owner from his own terminal, or the parent): no new grants; waiting agents' `wait` exits 3; the holder's game commands are refused with exit 3, so it quits and releases. `resume` grants again.
- **The parent:** `preempt --parent` (quits the game, restores the baseline, revokes the token), `reclaim --parent` (the same for an expired lease), `watch` (in the background; exits 4 with an `ALERT:` line on an expired lease, a stale holder (no game command for 10 minutes), a skipped grant, blocked grants, a pause, or a saves difference at a release). The parent's own emergency and integration runs: `--parent` on `game.py`, `build_mod.py` and `regress.py` skips the holder check and is logged in `events.log`; its normal integration runs queue as holder `integration`.

**Guards in `game.py`:**
- `run` and `load` take only the saves configured in the lock's config: `test`, `slot` and any added with `--allow-save`, by full name ([Test saves](#test-saves)). A missing name is refused (the newest save is never loaded), and so is every load while no save is configured.
- After every load, `gmtest_nosave()` locks saving for the session; its absence (a build without the tests, or not Ghost Mode) is an error.
- `start` refuses unless the installed `modGhostMode` (its `.built-by-build_mod`: ref and commit) is the build the holder installed this turn, so no agent tests the previous holder's install.
- `exec` refuses calls that load or save a game (`autoload`, `SaveGame`, the test save makers: `DENIED_EXEC`); saving the test-only slot is the parent's.

**Prohibited for agents** (they bypass the lock): calling `rw3d_cli` directly, installing with `--scripts`, copying saves by hand, editing the settings files, `--parent`.

### modAutomation

Markers (each line `[Automation] <event> key=value ...`):

| Marker | Hook |
|---|---|
| `main menu` | `@wrapMethod(CR4CommonMainMenuBase) OnConfigUI` |
| `game started restored=<bool>` | `@wrapMethod(CR4Game) OnGameStarted` |
| `ready` | `@wrapMethod(CR4Game) OnAfterLoadingScreenGameStart` (loading screen gone) |

Exec functions: `autostatus()`, `autosaves(optional count)`, `autoload(optional file)`, `autoresume()`, `autoquit()`, `autoconfig(optional group)` (list the options menu groups, or one group's variables with display name, label, type, value and visibility), `autoconfigset(group, var, value)` (set a variable and save the user settings). Errors log `[Automation] error ...`, which `game.py` treats as a failure.

Input simulation: `autocast(sign, optional hold)`, `autocastrelease()` (see [Input simulation](#input-simulation)). Lock-on: `autolock()` hard-locks onto the nearest living hostile within 15 m (or `autolock(false, <range>)`), as the lock-on button does (`ProcessLockTarget`, `HardLockToTarget(true)`); `autolock(true)` releases it.

Probes, which report state (see [Setting up Geralt and the world](#setting-up-geralt-and-the-world)):

| Probe | Reports |
|---|---|
| `autoplayer()` | Level, experience, skill points, money, difficulty; vitality, stamina, toxicity, adrenaline (current/max); position, game time, player state (`Exploration`, `CombatSteel`, ...), in combat, immortality mode |
| `autoskills()` | Every learned skill: name, `ESkill` value, level/max level, slot (-1: not equipped), `canUse`; slot counts |
| `autoinv(optional all)` | Equipped items (all items with `true`): name, category, quantity |
| `autobuffs()` | Active effects with time left (-1: permanent) |
| `autoattr(attr)` | One of Geralt's attributes (`base`, `mult`, `add`), e.g. `autoattr('staminaRegen')` |
| `autoactors(optional range)` | Actors within 30 m (or `range`): template, name, attitude, level, health fraction, alive, distance |
| `automerchants(optional range)` | Merchants (NPCs tagged `ShopkeeperEntity` or `Merchant`) within 200 m (or `range`): name, distance, tags |
| `autoshopkinds(tag)` | The number of item kinds the NPC tagged `tag` holds |

Shops and loot (vanilla scripts only, so they work with Ghost Mode off): `autospawn(path, tag)` spawns an entity template 3 m in front of Geralt and tags it (paths with backslashes in double quotes, e.g. `autospawn("quests\secondary_npcs\master_blacksmith.w2ent", 'yoana')`); `autoshop(tag, optional hours)` moves game time on by `hours` and opens the NPC's shop as the shop dialogue does (`AutoBalanaceItemsWithPlayerLevel`, then the inventory menu, whose opening runs `UpdateLoot`; close it with `game.py resume`); `autoshopempty(tag)` empties the NPC's inventory (as if everything were bought: the next restock shows); `autolootroll(list, n)` queues a loot list `n` times into a spawned test merchant (`AddItemsFromLootDefinition`, then balance) and logs the kinds of each roll: it crashes the game after some dozens of rolls ([below](#loot-lists-crash-the-game)).

Prices without a menu (Ghost Mode's test scripts, ECON): `gmtest_spawnat(path, tag)` then `gmtest_econ_probe(tag)` lists what that merchant asks and pays for reference items and his fees. His type and region come with his entity file, wherever Geralt is ([development.md](development.md#testing-in-game), "Prices in tests"): they are his inventory's tags. `gmtest_econ_tags_probe()` lists them for the enchanter, Blood and Wine's spawnable craftsmen (none) and the Novigrad weaponsmith; a test gives a spawned merchant another region by setting his inventory's tags (`npc.GetInventory().SetTags(...)`, as `gmtest_econ_e1` does for the Beauclair blacksmith). `gmtest_econ_fees_probe()` logs the repair and socket fees at the enchanter, a columnless Blood and Wine blacksmith and the Novigrad weaponsmith; `AddSlot(id)` adds a socket to an item by script.

- **Spawn code again:** a test can call an entity's `OnSpawned` again with a local `SEntitySpawnData` (`spawnData.restored = true` for a load from a save); it runs 5.x's body and every wrapper (a merchant's funds at a restored spawn, ECON).
- **Talking by script** (`OnInteraction("Talk", thePlayer)`, ITEM-02's and ECON-08's restock checks) starts the merchant's scene, and `status` reports `scene=true` until the game quits, also after the scenes are stopped and the merchant removed: run such checks last in a launch.
- **The contract negotiation popup** opens by script (`OpenMonsterHuntNegotiationPopup` on the HUD's `DialogModule`) and closes at once with `theGame.CloseMenu('PopupMenu')`; repeated openings leave no menu open (ECON-09). An offer goes through `DialogueSliderDataPopupResult`, as the popup's accept button calls it.

Rebuild and reinstall after changing it with the build command in [Quick start](#quick-start) (without `--enable`). `build_mod.py --scripts <dir>` builds any folder of scripts (laid out like `content\scripts`) instead of a branch's changes.

It stays enabled in `mods.settings`, also for normal play. That's harmless (it only logs and adds exec functions), but saves made with it list it in their `.json` metadata. Disable it with `Enabled=0` if that matters.

## Setting up Geralt and the world

### Skill trees

Ghost Mode supports both of 5.x's skill trees ([feature-mapping.md](feature-mapping.md#two-skill-trees)), so skill tests run on both. `skilleq` equips any skill whatever the tree, so a test can equip the classic skill (e.g. `S_Sword_s01`) or the new tree's counterpart (`S_Sword_s35`) directly. The tree the player has chosen is 5.x's hidden setting `RemasterCombat`/`UseLegacySkillTree` (`autoconfigset(RemasterCombat, UseLegacySkillTree, true)`; it saves into the real settings file, which the lock's release restores); code that special-cases shared skills reads it. **Verified**: `autoconfigset` sets it (`autoconfig(RemasterCombat)` lists nothing, the group being hidden), and with it on `skilleq(S_Sword_s01)` equips the classic Whirl, which then works in a fight. *Not yet tested:* the classic character screen itself (buying and equipping skills by hand).

**Timing of held special attacks:** each `game.py exec` call adds about a second, so a Whirl pressed in one call drains its stamina before a release in the next call arrives. Press, check and release in one call (`exec --wait 500 "gmtest_stam02_press(false)" "autostatus()" "gmtest_stam02_release(false)"`).

### Exec functions

Tests that need a particular character (level, skills, gear) or a fight set it up with the game's own exec functions, called through `game.py exec` like any other. All of them are cataloged by topic in [console-commands.md](console-commands.md) (generated by `tools/exec_catalog.py`). The script source is the reference for what each one does on 5.x; online command lists describe the legacy game.

**Vanilla debug output is not logged.** Vanilla functions that only log (`logskills()`, `printinv()`, `statsplayer()`, `printbuffs()`, `printdiff()`, ...) run, but nothing reaches `scriptslog.txt`: in the release build only mod scripts' `LogChannel` output appears. `pos()` and similar show a HUD message instead. Read the state with `modAutomation`'s probes (above).

### Test helpers by area

Ghost Mode's own test functions (`modGhostMode/scripts/local/gm/tests/`) that set up fights and read enemies; the test files' header comments are the full reference. Paths built in script take forward slashes (`LoadResource("living_world/enemy_templates/...")`), which avoids backslashes before letters in strings. Spawnable entity paths can be listed from the uncompressed path table of `content\content0\bundles\*.bundle` (`grep -a -o` for `...\.w2ent`; `ep1.bundle` holds Hearts of Stone's).

**Enemy levels and stats** (AI-01, `tests/gmTestsAi.ws`): `gmtest_ai01_spawn()` spawns fifteen frozen hostile test dummies (bandits at several levels and one set to `ENGT_Guard`, wolves, a bear, monsters); their level bonuses come by timer, so read them in a later call with `gmtest_ai01_read()` (each one's level, per-level abilities, High/Deadly and health against legacy's formula); `setlevel(N)` then `gmtest_ai01_recalc()` recomputes them as combat start does. No guard stands near the test save (`gmtest_ai01_guards(500)` finds none); the guard rule is tested on a spawned human set to `ENGT_Guard`.

- **A real finisher on death:** `gmtest_ai01_fin_a(d)` draws the steel sword, turns Geralt to the flattest of 16 directions and spawns a lone hostile human d levels above him 1.8 m away; `gmtest_ai01_fin_b(d)` kills it with a scripted hit of the sword and reads `CanPerformFinisher`'s answer. The finisher needs the victim within 0.4 m of Geralt's height, ground with room around it and no other attacking enemy near; on the test save's slope a dummy straight ahead may stand too low (`gmtest_ai01_fin_why()` lists the conditions). Wait about 5 s between kills: the finisher animation runs.
- **Enemy stats by kind** (AI-03 to AI-05, `tests/gmTestsAi03.ws`): `gmtest_ai03_spawn()` spawns thirteen frozen hostile enemies at Geralt's level, 4 m apart (drowner, nekker, griffin, golem, arachas, wolf, troll, fiend, a Nilfgaardian deserter in plate, a renegade with an axe, and 5.x's `mq1060` enemies: Reinald, the red-plague creature, a plague victim), plus the Caretaker and a shade; `gmtest_ai03_read()` in a later call logs each one's abilities, health, armor, resistances, attack power and weapon and checks them against legacy's data; `gmtest_ai03_probe(i)` makes scripted hits both ways with the i-th (the damage probe; draw the sword first).
- **A real enemy attack on Geralt:** spawn the enemy as a frozen dummy near Geralt, then `gmtest_ai03_fight_a(i)` runs that one at normal speed with Geralt immortal and the damage probe on; `gmtest_ai03_fight_b(i)` some seconds later logs every hit's steps and freezes it again.
- `gmtest_dummy(<path>, <level>, <distance>)` spawns any entity as a test dummy (forward slashes; level 0: the entity's own); `gmtest_dummy_info()` lists its stats. `gmtest_ai05_torch()` gives a frozen bandit Hearts of Stone's NPC torch (`Torch Blunt Burning`), reads its damage in the bandit's hand and logs a scripted torch hit on Geralt.

### Loot lists crash the game

Queuing loot lists into the same inventory over and over in one launch (`AddItemsFromLootDefinition`) ends in an access violation (exit code `0xC0000005`, no crash report) a few seconds after a call. It is 5.x's engine: with Ghost Mode off the same path ends in a hang after a few hundred rolls; Ghost Mode's data (not its scripts, not a bad list entry) makes it come sooner, after some dozens. Rules:

- A merchant's normal restock is not affected (emptied, game time moved on, the shop opened as the dialogue does: hundreds of restocks in one launch without a crash).
- Do not add list rolls to the regression. LOOT's `gmtest_loot()` (its own SUMMARY) runs once in a launch of its own; quit after it.
- Ghost Mode adds items to a shop with `AddAnItem`, not by queuing a list at every opening (Yoana's master items, CRAFT-10; [open question](open-questions.md#mod-scripts)). A Yoana spawned from her entity file (`quests\secondary_npcs\master_blacksmith.w2ent`) lacks her quest tag `sq108_blacksmith_woman` (`gmtest_craft10_stock('<tag>', true)` adds it and logs her master stock). A queued list skips the schematics Geralt knows.
- To tell a crash from an exit, watch the process's exit code (a script holding a process handle, `GetExitCodeProcess`).

### Saves and autosaves

Changes made by exec functions are not saved unless the game saves; `game.py run test` always starts from the test save's unchanged state. Every load locks saving with `gmtest_nosave()` until the game quits, but some saves come before it or around it:

- **Level-ups request autosaves** (`RequestAutoSave("level gained")`), and the autosave rotation deletes the oldest autosave in the folder. `game.py`'s load lock covers them; a session started any other way calls `gmtest_nosave()` before levelling.
- **Teleports can start quest scenes** (`tptopos` into the White Orchard bandit camp starts a prologue scene, which autosaves): check `game.py saves -n 1` after teleporting and report it.
- **A new game writes a checkpoint** before the lock can run (see the table above).
- The lock's grant backs up the saves and its release reports every save gone, new or changed. Restore nothing into the live folder without the owner.

**Saves made by tests** (save impact checks such as `gmtest_arm09_mksave`, `gmtest_diff04_save_mk()`): `theGame.SaveGame(SGT_Manual, -1)` writes a new manual slot, but nothing is saved while a hostile NPC is near (Geralt in combat): remove test dummies first (`gmtest_dummy_clear()`, `killall()`). `game.py saves -n 1` names the new slot. `gmtest_xp08_vit_b(true)` lifts `gmtest_nosave()`'s lock for one such save; call `gmtest_nosave()` again once `game.py saves` shows it. A new manual slot rotates no autosave. These are parent-only runs (`exec` refuses `SaveGame` and the save makers).

**An NPC restored from a save is not re-levelled at the load:** its level abilities come back from the save and its level is computed again only at its next recompute (combat start, Geralt's level-up, an option or mode change); a test calls `RecalcLevel()` to stand in for the fight's start (verified on the test-only slot, DIFF).

**Removing the mod** for a check: set `Enabled=0` under `[modGhostMode]` in `mods.settings` (with the game closed; the parent's job, as the lock restores the file at the release), load the save, then restore the file; `gmtest_regress()` failing to run confirms the mod is off.

**Item definitions** (ECON): the definitions manager reads an item's definition without adding it (`GetItemPrice`, `GetItemCategory`, `GetItemLocalisationKeyName`, `ItemHasTag`): thousands of such reads in one exec call take well under a second (`GMTest_econdata`). An item emptied by an `extend` reads price 0, category `default` and no name key. **NG+ definitions** (`items_plus`, `abilities_plus`) are read only in an NG+ game; neither test save is one, so NG+ data is checked by the generators' `--verify` only.

## Input simulation

The game has no way to fake a key press, but a script can call the input handler's events itself with a made-up key state. **Verified** for casting signs (STAM-01):

- `SInputAction`'s fields are declared `import const`, but a script can still set them on a local variable (`action.aName = 'CastSign'; action.value = 1; action.lastFrameValue = 0;` is a press, `0` after `1` a release), and pass it to an event: `thePlayer.GetInputHandler().OnCastSign(action)`. Everything behind the event runs as for a real key: the checks, Ghost Mode's wrappers on the event, the sign states, stamina.
- `modAutomation`: `autocast(ST_Igni)` presses the cast input with that sign selected, `autocastrelease()` releases it. Each logs the sign, `casting`, stamina and player state. Ghost Mode's own `gmtest_stam01_press/release` do the same without depending on `modAutomation`.
- **Held keys cannot be faked that way.** The game reads the real key state (`theInput.IsActionPressed('CastSign')`, `GetActionValue('CastSignHold')`) to decide on an alternate cast (`W3SignOwnerPlayer.ChangeAspect`) and to keep a channel going (`ShouldStopChanneling` in the sign's `Channeling` state). `autocast(ST_Igni, true)` sets a flag that `modAutomation`'s wrappers of those two functions answer as for a held key, until `autocastrelease()`. The hold lasts as long as the calls in between take (each `game.py exec` call about `--wait` ms).
- Casting needs its conditions as in play. Every cast, normal or alternate, needs the base sign cost (40 with Ghost Mode) to start. Sign cooldowns (STAM-01) block recasting the same sign; for repeated casts set `GMSignCooldown` and `GMAltSignCooldown` to 0 with `autoconfigset` (the lock's release restores them).
- Measuring a held cast: `gmtest_stam03_chan_a(<stamina>)`, `autocast(<sign>, true)`, then `gmtest_stam03_chan_b()` between calls and after `autocastrelease()`. It sums the per-frame channel drains (amount, frames, first and last time) and logs the sign entity's state.
- **Alternate Axii in tests:** with both alternate Axii skills equipped, 5.x casts the classic one (`ChangeAspect` checks `S_Magic_s05` first), so unequip it to test Puppet (`S_Magic_s31`): `autoskills()` shows its slot, `skilluneq(<slot>)` removes it, and check again, since slot numbers shift. The puppet lands on a human (e.g. `gmtest_stam06_bandit()`); on that bandit it is gone again within about 1.5 s (its forced hostile attitude), so read it when the channel ends (the test probe on `W3AxiiEntity.OnEnded`, logged with `gmtest_probes(true)`), not afterwards.
- **Axii's confusion on the frozen test dummy** (ENCH-14): a real Axii's confusion can outlast its duration on the frozen dummy (its time left goes negative) and survive `RemoveAllBuffsOfType`, with no `OnEffectRemoved`; other times it ends within about 1.5 s. Read what a cast applied when it ends (the test probe on `W3AxiiEntity.OnEnded` stores it in `thePlayer.gmTestAxiiEnd`; `gmtest_ench14_count`), and test removal with effects added by script (`gmtest_ench14_stacks`).
- Other conditions as in play: the sign's skill (alternate casts need the alternate skill equipped: `S_Magic_s01` to `s05` in the classic tree; in the new tree Aard, Yrden and Quen use the same (shared) skills, Igni `S_Magic_s28` and Axii `S_Magic_s31`), stamina, and for Axii a hostile target in range. Axii's alternate (puppet) aborts unless held about 2 s.
- **Several signs in a row:** casting another sign ends Quen's shield (its entity's values then read 0), so read each sign's entity before the next cast (`gmtest_ui03_cast(sign)`, `gmtest_ui03_casts(sign)`). The sign cooldowns are per sign: Quen, Yrden and Axii can be cast a few seconds apart with the cooldown option left at 5.
- **Hits interrupt casts.** In a fight, run `god()` first (no hit reactions); otherwise casts fail at random.
- **A scripted hit does not break a channel.** A hit through `theGame.damageMgr.ProcessAction`, even `EHRT_Heavy` with `EAHA_ForceYes`, leaves a held Firestream channeling (SKL-07). To test an interrupted cast, abort the sign (`OnSignAborted(true)` on the sign entity, `gmtest_skl07_foa_abort()`).
- **Out of combat, stamina regen is 100% of max per second**, so stamina read after an out-of-combat cast says nothing about its cost; measure costs in combat.
- Guarding: `thePlayer.SetGuarded(true)` from a script (see the table above).
- **Drinking from a quick slot:** equip the potion in `EES_Potion1` and call `W3PlayerWitcher.OnPotionDrinkKeyboardsInput(EES_Potion1)`, what the slot's key calls (`DrinkPotionFromSlot` itself is private; `gmtest_alch04_slot`).
- **Northern Wind's freeze is short:** after a scripted throw (`gmtest_alch14_throw`) read the frozen dummy within about a second of the release; 3 s later it has thawed.
- Special attacks: calling `CPlayerInput.OnCbtSpecialAttackLight/Heavy` with a press starts Whirl or Rend (needs `S_Sword_s35` / `S_Sword_s02` equipped, or the classic `S_Sword_s01`, and a drawn sword in combat), and the release ends it; no held-key simulation is needed (the attack runs until the release event). **Verified** (STAM-02, `gmtest_stam02_press/release`). Normal attacks: `OnCbtAttackLight` press and release starts a light attack; the sword heavy attack's event checks the real key's activation time (`theInput.GetLastActivationTime('AttackHeavy') < 0.2`), so start it with `thePlayer.SetupCombatAction(EBAT_HeavyAttack, BS_Released)`. Dodge and roll: `OnCbtDodge` / `OnCbtRoll`. Bombs: select one (`EquipItemInGivenSlot(id, EES_Petard1, false)`, `SelectQuickslotItem(EES_Petard1)`), then `SetupCombatAction(EBAT_ItemUse, BS_Pressed)`, a moment later `BS_Released` (the item input event depends on real key state; press and release in one frame throws nothing). **Verified** (STAM-03, `gmtest_stam03_act_a/b`, `gmtest_stam03_bomb_a/release/b`).
- Quick and aimed throws (`gmtest_skl06_throw(pressed, aimed, bomb)`): a press through `SetupCombatAction(EBAT_ItemUse, BS_Pressed)` throws a quick bolt or bomb (not aimed). An aimed **bomb** needs `thePlayer.SetThrowHold(true)` before the press (the throw animation's `ThrowHoldTest` event then enters `AimThrow`); while aiming, the buffered release is not processed, so release with `BombThrowRelease()` (test-only `GMTestBombThrowRelease`). - **Baseline builds:** to see what vanilla does with the same probes, build a branch that is the current commit minus the feature's file (`git read-tree`, `git rm --cached`, `git commit-tree` with a temporary `GIT_INDEX_FILE`; a temporary worktree in the scratchpad fails on this repo's long paths) and run the same test.
- Finishers: `gmtest_stam06_bandit()` spawns a hostile human (finishers need a human male; the template is `dlc\dlc7\data\characters\sq107_bandit_lvl1_mortal.w2ent`: the non-`_mortal` one is immortal and never drops below 1 health), `ForceFinisher(true)` (vanilla) forces the next killing blow into a finisher, `gmtest_stam06_weaken()` puts the bandit at 1 health 1.5 m in front of Geralt and confuses it (Axii's effect, so it does not block), then a light attack (`gmtest_stam06_fin_a()`) kills it with a finisher. **Verified** (STAM-06).

## Findings

### Hang after loading a save

If the game shows a black "Loading" screen after the save has loaded (`ready` logged) and stops answering exec calls, also without any mods, check that it renders on the right GPU: on a system with several display adapters (an integrated GPU, a virtual display adapter) it can end up on one without dedicated memory. Check the game's dedicated GPU memory per adapter (`(Get-Counter '\GPU Process Memory(*)\Dedicated Usage').CounterSamples` filtered on `pid_<witcher3 pid>`; several GB on the right GPU), or the vendor's tool (`nvidia-smi`). A restart of the computer fixed it when it happened.

### Menus

- The inventory's stats view opens with `C` (`send_key.ps1 type c`); its rows do not react to the arrow keys or to a cursor moved by `SetCursorPos` (the game reads raw mouse input; `mouse_move.ps1` moves it). Check panel values from script instead: `GetPlayerStatsGFxData(menu.GetMenuFlashValueStorage())` with any menu open (e.g. `ingamemenu()`), reading the lines back with `GetMemberFlashArray` / `GetMemberFlashString` (`gmtest_panel`).
- If another window covers the game, minimize it, then run `focus_game.ps1`.

### Launch

- **Verified:** starting `bin\x64_dx12\witcher3.exe` directly (working directory `bin\x64_dx12`, Steam running) skips REDlauncher, and the process started is the game itself (no relaunch through Steam). Arguments pass straight through; no Steam launch-option change needed.
- *Unverified alternative:* the Steam launch option `--launcher-skip` ([Steam guide](https://steamcommunity.com/sharedfiles/filedetails/?id=2902047062)), only needed when Steam must start the game.
- Untested: launching while Steam is not running.

### Startup screens

Before the main menu the game shows a queue of screens (`CR4Game.PopulateMenuQueueMainOnce`), each a menu:

| Menu | What it is | Without input |
|---|---|---|
| `StartupMoviesMenu` | Logo videos | Ends after about 45 s |
| `RecapMoviesMenu` | Story intro video ("Space Skip") | Waits |
| `StartupExperienceMenu` | CD PROJEKT RED account sign-in, then telemetry consent. Shown only on some launches (`EvaluateStartupLaunchCriteria`) | Waits |

- **Verified:** closing each with `autoresume()` (`CMenu.CloseMenu()`) moves on to the next, and then the main menu appears. `game.py start` does this as soon as the game answers exec calls (about 8 s after launch). Closing the sign-in screen answers neither the sign-in nor the telemetry question.
- Space as a key press also skips the videos (`SkipShowWithAnyKey=true`); not needed.

### Loading and pause state

- **Verified:** `theGame.LoadLastGameInit()` (what Continue calls) loads the newest save from the main menu. `ListSavedGames` plus `LoadGameInit(info, false)` loads a named save; the list is newest first.
- **Verified:** marker order on load: `loading save=...`, `game started restored=true`, `ready`. Right after `ready` the game answers exec calls, is not paused and has no menu open.
- **Verified:** the vanilla exec function `ingamemenu()` opens the pause menu; `autostatus()` then reports `paused=true menu=CommonIngameMenu`, and `autoresume()` closes it (`paused=false menu=none`). So pause tests need no Esc key either.

### rw3d_cli

[Rusty Witcher 3 Debugger](https://github.com/SpontanCombust/rusty_witcher_debugger) CLI v0.8.0 (2024-08), downloaded from its GitHub release into `tools/rw3d/` (git-ignored). To get it: `gh release download v0.8.0 -R SpontanCombust/rusty_witcher_debugger -p "*windows-msvc.zip"`, then unzip into `tools/rw3d/`.

- **Verified:** `exec "<call>"` runs any exec function, with arguments, without keyboard or focus, at the startup screens, the main menu and in game. With `-l output-only` it prints just the function's `LogChannel` output.
- **Verified:** rw3d_cli always waits the full response timeout (`-t`) for more output after the reply arrives, so `-t` is the time per call: 200 ms gives 0.27 s per call. `game.py` uses 500 ms.
- **Verified:** for about 5 s after launch the game does not answer (the CLI may even panic), and during loading it may answer late. A command can run even when the CLI reports "Waited too long for the response", so `game.py` never retries a command; it only retries the harmless `autostatus()` until the game answers.
- **Verified:** `autoquit()` exits the game before the reply is sent, so its call always "fails"; `game.py` then just waits for the process to exit.
- **Failed:** do not use `reload`: it never reports back, and the game then runs without the mods' script blobs (it recompiles vanilla plus loose mod scripts only). Use `build_mod.py` and a game restart instead.
- **Failed:** `rootpath` and `modlist` time out: the game answers, but this CLI version does not accept the reply (probably a 5.x protocol change). Not needed.

### Two script blobs

- **Verified:** two mods with a `precompiled.rsblob` each (`modAutomation` and `modGhostMode`) load together, both at priority 100: both mods' exec functions and wrappers work. How blobs that change the *same* method combine (2026-11-13: the first mod by folder name takes precedence) is in [development.md](development.md#how-the-game-loads-mod-scripts).

### ReShade

The owner's install has ReShade (`bind_dx12\dxgi.dll`, with RenoDX and DLSS 5 add-ons). **Some launches crash during startup with it** (Crash Reporter about 10 to 15 s in, before the main menu; `ReShade.log` ends right after the DLSS add-on hooks `nvngx_dlss.dll`), and `game.py` then times out waiting for the main menu. Seen three times on 2026-11-13, with different mod sets that ran cleanly with ReShade off. With the owner's OK, disable it for a run by renaming `dxgi.dll` to `dxgi.dll.reshade-off`, and rename it back afterwards. A startup crash with ReShade installed is no evidence against the mods.

### Close

- **Verified:** `autoquit()` exits in about 2 s, from the main menu or in game. Fallbacks in `game.py`: WM_CLOSE to the game window (also exits within seconds, no dialog), then `taskkill /F`.

### Keyboard and screenshot fallback

For situations the mod cannot handle (e.g. a hang before scripts run, checking what is on screen, real input in a menu). Scripts in `tools/`, run as `powershell -NoProfile -ExecutionPolicy Bypass -File tools\<script> ...`; all need the game in front:

- `focus_game.ps1`: brings the game window to the foreground (key presses go to the foreground window).
- `send_key.ps1 <key> [count] [delayMs]`: `space`, `esc`, `enter`, `tilde`, `e`, `backspace`, `up`, `down`, `left`, `right` as hardware scan codes (arrows as extended keys). `send_key.ps1 type <text>` types text as scan codes. It only taps keys; a held key needs `SendInput` key-down and key-up events.
- `screenshot.ps1 <out.png> [-Region x,y,w,h]`: captures the primary screen. Save screenshots in the session scratchpad, not the repo.
- `mouse_move.ps1 <X> <Y> [-Click]`: moves the game's menu cursor to a screen pixel with relative raw moves, optionally left-clicks. Hovering an item in the inventory shows its tooltip, clicking a tab switches it (**verified**: `r4inventory()` opens the inventory, then hover and screenshot).

Rules for input:

- **Verified:** the game reads hardware scan codes (`SendInput` with `KEYEVENTF_SCANCODE`). `~` opens the console, letters type, Enter runs the command. Shift does not reach the console (`()` typed as Shift+9/Shift+0 comes out as `12`); no-argument exec functions work without `()`. Unicode key events and clipboard paste type nothing.
- **Verified:** menus navigate with the arrow keys and Enter (open the pause menu with `exec "ingamemenu()"` first). E does not select in menus, and an injected E in the inventory runs no item action: send the action's navigation code to the menu instead (`gmtest_menuinput("enter-gamepad_A")` calls the inventory's `OnInputHandled` as its Flash does for the key). `SetCursorPos` does not move the game's cursor (it reads raw input); relative `mouse_event` moves and clicks do (`mouse_move.ps1`).
- **Verified:** menus opened by script (`gmtest_shopopen`, `gmtest_craftopen`, `gmtest_smithopen(tag, 'AddSockets')`, `ingamemenu()`) then work with real input. In the shop, `send_key.ps1 space` sells the hovered item of Geralt's, but buying takes a left double-click on the merchant's item (`mouse_event` down, up, down, up); "Sell Junk" needs Space held about two seconds (scan code 0x39 down, wait, up). In the crafting and repair menus, click the "Craft Item" and "Repair" buttons (E does nothing in the crafting menu) and the confirmation's "OK". In the options menu a click only selects a row: change toggles and lists with the left and right arrow keys; a preset is a click on its name. Lists scroll with the mouse wheel (`mouse_event` 0x800, ±120 per notch). `type j` opens the journal, `type k` the character menu, `esc` closes them.
- HUD messages (`DisplayHudMessage`) may not show up in a screenshot (perhaps hidden by a tutorial hint): results come from the script log instead.
- **5.x's HUD shows no combat log**: a real kill shows nothing on screen; read the log's messages by script (a test wrapper of `W3GameLog.AddMessage`). Level-ups by `levelup()` or `addexp(N)` show no HUD message.

## Test saves

`game.py run` and `load` (and `regress.py --save`, default `test`) load only saves the machine has configured: save file names differ on every machine, so they live in the lock's config (`%LOCALAPPDATA%\TGM\config.json`), not in the repository. Two saves are needed:

- **The test save** (`test`): White Orchard, just past the tutorial, near Vesemir and Roach. Geralt is level 1 with no skill points, the starting gear (Long Steel Sword, Witcher Silver Sword, starting armor), 250 crowns, all five signs; difficulty Blood and Broken Bones (`EDM_Hard`). Made with `modGhostMode` and `modAutomation` installed. Tests build the character they need with exec functions after loading ([Setting up Geralt and the world](#setting-up-geralt-and-the-world)), so the save itself stays a clean level 1 start; it is never saved over (every load locks saving).
- **The test-only slot** (`slot`): a save of the same playthrough with Geralt at level 20, for tests that need a higher level than `setlevel` on the test save gives safely (levelling up requests autosaves) and for save-and-load checks. It is the one save tests may save over, and never a personal save. Only the parent saves it, with `gmtest_diff04_lsave_save(key)`, which saves over the one manual save whose name contains `key` and refuses when none or several do: pass a part of the slot's name unique among the saves (its last part; check `game.py saves`). The slot's file name changes at every save, so update the config afterwards.

**On a new machine**, with the game set up for the project and `modGhostMode` and `modAutomation` installed and enabled:

1. Start a new game (difficulty Blood and Broken Bones), play through the tutorial to White Orchard and make a manual save near Vesemir and Roach: the test save. Change nothing else first.
2. Load it, `setlevel(20)`, and make a second manual save: the test-only slot.
3. Find their file names (without `.sav`) with `python tools/game.py saves` or in `Documents\The Witcher 3\gamesaves`.

**Configure them** once per machine:

```bash
python tools/game_lock.py config --test-save NAME --slot-save NAME
python tools/game_lock.py config --allow-save NAME      # another save game.py may load, by full name (repeatable)
python tools/game_lock.py config --disallow-save NAME   # take it off that list
```

`game_lock.py config` with no options prints the config. Then:

```bash
python tools/game.py run test --holder AREA:TOKEN      # the test save
python tools/game.py run slot --holder AREA:TOKEN      # the test-only slot
python tools/regress.py --holder AREA:TOKEN            # the regression on the test save
```

Without a configured save, `run` and `load` refuse with a hint to this section.
