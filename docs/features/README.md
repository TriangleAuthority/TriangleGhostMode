# Feature map

The map of Ghost Mode's changes for the 5.x port: what each feature does, which change units implement it, what 5.x means for it, and how it is ported. The method is in [feature-mapping.md](../feature-mapping.md); how to write the port is in [development.md](../development.md).

| File | Content |
|---|---|
| [pillars.md](pillars.md) | The design pillars every feature serves |
| [balance.md](balance.md) | Player power and balance: the rules (B1–B10) for skills, perks, mutations, potions and gear, the two-tree plan, the archetypes and the checklist for every balance-relevant change |
| [ledger/](ledger/README.md) | Reference data for balance: every source of every power stat in legacy Ghost Mode and 5.x (skills and perks, potions and decoctions, gear, mutations) |
| `<area>.md` | Feature entries for one area (below) |
| [units.csv](units.csv) | Generated by `tools/change_units.py`: every change unit Ghost Mode made |
| [attribution.csv](attribution.csv) | Hand-maintained: which feature(s) each unit belongs to |
| [coverage.md](coverage.md) | Generated: units no feature claims yet |
| [deviations.md](deviations.md) | Generated by `tools/deviations.py`: every recorded deviation from legacy, by feature |

**How the work runs** (as agreed with the project owner):

- One small slice at a time: read the legacy units (`git show master:` vs `legacy-GM:`, 5.x in `vanilla-5.x:`), port with wrappers where possible, add a `gmtest_*` function, build, test in game, update the feature entry and this page.
- `tools/build_mod.py --ref 5.x-GM` builds the **committed** branch: commit on `5.x-GM` (worktree `../TGM-5x-GM`, next to this checkout) before building; amend while iterating. Docs live on `master` (this checkout).
- Commit and push only when the project owner says so; at the end of a slice, report the result and ask.
- The first version reproduces legacy's behaviour, gaps included; improvements go to the feature's **Later** list ([why](../feature-mapping.md#legacy-behaviour-first)).
- Scripted input and its limits (held keys, the heavy attack, bombs), the probes and the test save: [game-automation.md](../game-automation.md). If the game hangs on "Loading" after loading a save, check that it runs on the dedicated GPU (same doc). Minimizing the Claude window to bring the game to the front is allowed.
- Checks that need a save further into the story (a quest's scene, a contract, days passing) wait until after the first playable version: the owner runs them in a playthrough from each feature's **Open checks** (the owner's decision, 2026-11-02). Until then the port goes on without them.
- When a feature is finished, run the regression check in one game session (`gmtest_regress()` plus the panel check; see [development.md](../development.md#testing-in-game)) and add the feature's situation-free checks to it.
- Ghost Mode supports both skill trees: a feature that touches skills is ported and tested for the classic and the new tree ([feature-mapping.md](../feature-mapping.md#two-skill-trees)).
- A finished feature is audited by a new session that did not port it, then signed off ([audit](../feature-mapping.md#audit-signing-a-feature-off)).
- Feature entries follow the [template](../feature-mapping.md#feature-entry-template): short table values, verification per slice (real or scripted), open checks; measurements and investigations stay out of the repository docs.
- `python tools/unit_sweep.py <keyword> --unattributed` checks a mapping for missed units.
- Ghost Mode ships a script blob but must stay portable to loose scripts ([development.md](../development.md#principles)): `@replaceMethod` rather than a scope-based override where both work, every changed line marked `//modSigns`, no native wraps without the project owner's agreement; `python tools/check_modsigns.py` checks the last two before each script commit.
- Anything that fits no slice, feature, area or pillar goes into the misc bucket, [misc.md](misc.md), instead of being dropped or forced into a feature.

## Features with a save impact

Features whose port needs more than installing the mod (see [save compatibility](../feature-mapping.md#save-compatibility)). [ITEM-04](item.md#item-04-items-moved-to-level-scaling): `reacquire items` (expected): an Iris, Ofir armor, Ofir Sabre 2, a piece of Blood and Wine's first vampire set, Yoana's armor, the Nekker boots or the standalone starting gear held from before the mod keeps no fixed damage or armor and has no per-level damage or armor until obtained again; items already owned also keep the level and random bonuses they got (ITEM-02, ITEM-06, ITEM-08). Otherwise none: ARM's changed item stats and tags apply to items already owned (verified 2026-10-17, [ARM-01](arm.md#arm-01-armor-pieces-resistances-by-class-armor-by-level)); the Kaer Morhen schematics are granted at load and 5.x's "Starting Armor Upgrade schematic 1" removed ([ARM-12](arm.md#arm-12-kaer-morhen-set)).

Removing the mod from a save is not supported ([save compatibility](../feature-mapping.md#save-compatibility), the owner's decision, 2026-10-18); what it does, as facts for the release notes: mutations researched at legacy's costs show as partly researched under 5.x's costs again ([MUT-01](mut.md#mut-01-mutation-system-research-costs-and-housekeeping)); the Mutation Catalyst and its recipe become unknown items ([MUT-12](mut.md#mut-12-life-leech-and-mutation-catalyst-mutation-11)); the Kaer Morhen pieces disappear from the save, worn ones leaving their slots empty ([ARM-12](arm.md#arm-12-kaer-morhen-set)); the master weaponsmith and armorsmith tools become unknown items, and the items ITEM moved to level scaling (Iris among them) keep only their per-level damage or armor ([ITEM](item.md#save-impact)).
