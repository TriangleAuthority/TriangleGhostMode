# Development guide

How to write, build and test the 5.x port. Read this before changing the port on `master`.

[feature-mapping.md](feature-mapping.md) decides *what* to port and in which order. This doc covers *how*: which 5.x modding features to use, the conventions for this mod, and the build and test loop.

Status labels: **verified** means tested in game on 5.x; **compiles** means `wcc_lite compilescripts` accepts it but it has not been run in game yet; **unverified** comes from documentation or other sources and has not been tested here. Update the labels as tests confirm things. Questions nobody has answered yet are collected in [open-questions.md](open-questions.md).

## Principles

- **Prefer the least invasive way to make a change** (see [Port forms](#port-forms)). 5.x can merge script and XML changes from several mods at game start, so a mod that only adds override files survives CDPR patches and other mods far better than one that ships edited copies of vanilla files.
- **Small steps, each run in game before the next.** See [feature-mapping.md](feature-mapping.md#small-steps-verified-in-game). Every step passes the [compile check](#build-compile-install) and the in-game check.
- **Record the save impact** of every change (`none`, `reacquire items`, `cleardevelop`, `new game`). See [feature-mapping.md](feature-mapping.md#save-compatibility).
- **Keep the spirit of Ghost Mode, built on 5.x's systems.** Re-apply the intent of a legacy change to the 5.x code, not the legacy code itself.
- **Do not edit `vanilla-1.32`, `legacy-GM` or `vanilla-5.x`.** All mod work happens on `master` (or a short-lived branch off it, such as an area's `gm/<area>`).
- **Ship a script blob, but stay portable to loose scripts** (project owner, 2026-10-04). Ghost Mode ships `precompiled.rsblob` and uses scope-based overrides where only they can do the job. Many players combine mods, and Script Merger merges only loose scripts (blob conflicts are listed as not mergeable), so a loose-script version may be needed later. In it, every `@replaceMethod`, scope-based override and enum extension becomes a direct edit of the vanilla file; `@wrapMethod`, `@addMethod` and `@addField` stay. Keep that port mechanical: mark every changed line (`//modSigns`, see [Conventions](#conventions)), and never wrap a native function without the project owner's agreement (blob only, see [Annotations](#annotations)).

## Port forms

Use the first form that can express the change:

| # | Form | Use for | Details |
|---|---|---|---|
| 1 | **Scope-based override**, **enum extension** or **script annotation** (`@wrapMethod`, `@replaceMethod`, `@addMethod`, `@addField`), in a new script file | All script changes | [Scripts](#scripts) |
| 2 | **XML override through Ghost Mode's DLC** (`on_conflict="extend"` or `"replace"`) | Changing or adding abilities, items, loot and other definitions | [XML](#xml-and-csv) |
| 3 | **DLC mounter** in Ghost Mode's `.reddlc` | Attaching abilities or parameters to entity templates, registering XML, CSV, journal or other content | [DLC mounters](#dlc-and-mounters) |
| 4 | **Whole-file override**: the mod ships its own copy of a vanilla file at the same path | XML, CSV and other files the forms above cannot express. Not needed for scripts (see [Choosing a technique](#choosing-a-technique)). | The legacy approach. Every vanilla update to that file must be merged by hand. |
| 5 | **Binary resource edit** (`.w2ent`, `.journal`, ...) in REDkit | Values only stored in a binary resource, when a mounter cannot do it | [binary-files.md](binary-files.md) |

The feature entry records the form used ("Port form" in the [entry template](feature-mapping.md#feature-entry-template)), and why when it is 4 or 5.

| What | Path |
|---|---|

One file per vanilla class or system Ghost Mode changes; group into folders by feature area once there are several. `tools/build_mod.py` compiles everything Ghost Mode adds or changes under `modGhostMode/scripts/` into the blob. |

`tools/build_mod.py` turns these into an installable mod (see [Build, compile, install](#build-compile-install)).

## Conventions

- **Prefix everything Ghost Mode adds** so it cannot collide with vanilla or other mods: fields, methods and functions start with `GM`/`gm` (`gmStaminaCostMult`, `GMGetSignCooldown`), new classes with `W3GM`/`CGM`, exec functions with `gm`, log channels with `GM` (`LogChannel('GMStamina', ...)`), XML entries added (not overridden) with `GM_` or `gm_`.
- **Both skill trees.** Code that depends on a skill handles the classic tree's skill and the new tree's counterpart (e.g. Whirl `S_Sword_s01` and `S_Sword_s35`): read the one the player has equipped instead of hard-coding either; for a shared skill (one definition for both trees) special-case on the tree in use (Ghost Mode's tree profile, `GMIsClassicProfileInForce()`, SKL-02; 5.x's `UseLegacySkillTree` is not used) where the rules differ. XML changes to skill abilities cover both skills. See [feature-mapping.md](feature-mapping.md#two-skill-trees).
- **Tag every override with its feature ID** in a comment above it: `// STAM-01: stamina cost for light attacks`.
- **Mark every changed line with `//modSigns`** (project owner, 2026-10-04) in each replaced body: a `@replaceMethod`, a method in a scope-based override block, a whole-file override. An added or changed line carries `//modSigns` at its end (a comment may follow: `//modSigns: no heavy-attack multiplier`); a removed vanilla line or block leaves a comment line `//modSigns: removed ...` where it was; in a body with no vanilla counterpart (an override of an inherited method) or one Ghost Mode rewrote, every line is changed and carries the marker. Unchanged vanilla lines carry none. This is what separates Ghost Mode's code from the 5.x body when it is ported to direct edits of vanilla files (see [Principles](#principles)). `python tools/check_modsigns.py` compares each replaced body with `vanilla-5.x` and lists unmarked changes; run it before committing script changes.
- **Commit messages** name the feature IDs and the save impact when it is not `none`.
- **No absolute paths in the repository** (tools, docs, any branch): they expose details of a contributor's machine and break on anyone else's. Tools find install folders with `tools/paths.py` (Steam lookup, or the `W3_GAME_DIR` / `W3_REDKIT_DIR` environment variables) and refer to repository files relative to the script; docs write `<game>`, `<REDkit>`, `<Wwise>`, relative paths such as `../TGM-<area>`, or environment variables such as `%ProgramFiles(x86)%`.
- **Encodings:** scripts UTF-8 without BOM; XML UTF-8 with BOM; CSV as the 5.0 original. See [game-5.0-changes.md](game-5.0-changes.md#encodings).

## Scripts

### How the game loads mod scripts

**Ghost Mode ships its scripts as one compiled file, `mods\modGhostMode\content\precompiled.rsblob`**, built by `tools/build_mod.py` (pilot slices 1–2, **verified**). What the pilot established:

- A mod's scripts come either as **loose `.ws` files** in `content\scripts\`, or as a **script blob**, `content\precompiled.rsblob`. If a mod has a blob, **the game ignores that mod's loose scripts** (they are not loaded at all, without any error).
- **Loose scripts are compiled together with the vanilla scripts**, as in legacy versions. Annotations and whole-file overrides work there, but re-declaring an existing class or enum fails at game start: "Class 'W3PlayerWitcher' is already defined in current compilation unit", "Enum 'EEffectType' is already defined and 'isMod' is false".
- **A blob is compiled as mod code** (`isMod`), so it also allows **scope-based overrides** and **enum extensions**. Everything else works from a blob too: annotations, new classes and functions, and copies of vanilla files.
- The blob comes from `wcc_lite compilescripts <game scripts>\ -patch=<mod scripts>\ -out=<dir>` (REDkit), which also acts as the compile check. Blobs from REDkit build 1042178 load in game builds 1041720 (5.0) and 1044392 (5.0 hotfix) (verified). REDkit updated with game build 1090142 (Steam build 26269436, `wcc.log`: `wcc.exe [5.0.1090143]`); its blobs load in game 1090142 (verified: the regression in both trees, 0 failed). REDkit's `wcc.log` names its build in its first line.
- **A blob's change to a function beats other mods' loose scripts for the same function**, whatever the priority in `mods.settings` or Script Merger does ([mod.io guide](https://mod.io/g/the-witcher-3/r/what-does-the-remaster-mean-for-modding); matches our test: Ghost Mode's `@replaceMethod` of `W3PlayerWitcher.ReduceDamage` beat a loose mod's edited `playerWitcher.ws`, silently).
- **Between blobs that change the same function, the mod that sorts first takes precedence.** **Verified** (2026-11-13, two throwaway blob mods `modPrbA`/`modPrbB` on `W3PlayerWitcher` methods, priority 100 each, plus a rerun with B's code as `modPrb0`). Two blob mods, F (first) and L (later), at equal priority:
  - **Both `@replaceMethod`:** F's replacement runs and L's is dropped. No error or warning.
  - **Both `@wrapMethod`:** both run as a chain, F's wrapper outermost.
  - **F wraps, L replaces:** F's wrapper runs around L's replacement (`wrappedMethod()` returns L's result).
  - **F replaces, L wraps:** **L's wrapper is dropped silently.** F's replacement throws away everything below it, L's wrappers included.
  - So the game applies the mods from last to first: each `@replaceMethod` discards what is there, each `@wrapMethod` wraps it. The order is the folder names' order: `modPrb0` before `modPrbA` before `modPrbB`, and `modGhostMode` before `modGMMergeTestBlob` (the 2026-10-04 test, where Ghost Mode's replacement won), so the comparison ignores case.
  - **A `mods.settings` priority overrides the folder order; the lower number takes precedence** (**verified**: `modPrbB` at `Priority=50` with `modPrbA` at 100 gave B's results in every case, as renaming did). Two launches with this setting crashed at startup, but with ReShade installed; with ReShade disabled it ran cleanly, so the crashes were ReShade's ([game-automation.md](game-automation.md#reshade)).
  - For Ghost Mode: another blob mod's wrapper of a method Ghost Mode replaces (`@replaceMethod`) runs only if that mod's folder sorts before `modGhostMode`. Ghost Mode's wrappers survive another mod's replacement only if `modGhostMode` sorts first. A lower `Priority` in `mods.settings` does the same as sorting first, but it is a player's setting, easy to lose. Scope-based overrides and enum members in two blobs are not tested yet ([open-questions.md](open-questions.md#several-mods-with-script-blobs)).
- **One blob can call into another blob** when it is compiled against the other's code (**verified** 2026-11-13): `mod0PrbR2`, compiled by Script Merger Remastered's `Tools\WSCompiler\WSCompiler.exe compile --scripts <dir> --vanilla <game>\content\content0\scripts --reference <other mod's scripts folder or precompiled.rsblob> --out <dir>`, called `modPrbR1`'s global function and `@addMethod`, read its `@addField` and created its new class, in game, while sorting before it. The reference is declarations only: the output blob holds only its own code (416 bytes). Without `--reference` the same source fails to compile (unknown type). A blob built by `WSCompiler` (0.1.5) loads like one built by `wcc_lite`. `wcc_lite` has no reference option, so a mod that calls another mod's code is built with `WSCompiler`. Passing `--vanilla` each time avoids its `config` command, which writes a settings file into the Script Merger folder.
- **Script Merger Remastered** reads each blob's list of changed functions (keys such as `Functions\W3PlayerWitcher\ReduceDamage`, tagged added, wrapped, replaced, scope override) and lists clashes with other mods, but marks them "not mergeable": a blob holds compiled code, not source (**verified**, v1.4). **v3.01** (in `../Script Merger Remastered`) merges blobs, with mixed results (**verified** 2026-11-13, the owner's merges of throwaway blobs, read in game):
  - **Annotations only** (`modPrbA`/`modPrbB`: a replacement in one and a wrapper in the other, both directions, plus a clash): decompiled faithfully to loose scripts in `mod0000_MergedFiles\content\scripts\`, originals renamed `precompiled.rsblob.smr-disabled`; every change ran.
  - **With blob-only features** (`modPrbC`: a scope-based override block, an enum member, an event added by `@addMethod`, a wrapped native; clashing with `modPrbD` on one method): it also wrote a compiled mod, `modzzSMR_MergedCompiled` (229 KB; its blob names many vanilla `W3PlayerWitcher` members, so it likely carries a recompiled copy of the class). C's scope-added field and methods, its scope override of a vanilla method, the event, the native wrapper and its exec function **ran**; the enum member went into a whole-file copy of `types.ws`. But C's changed **default value was lost** (dropped already in its recovered source), the clash with D was not merged (D kept its own blob, C's replacement lost), the two mods' enum members still collided, and **every loose `@replaceMethod` from the earlier merge stopped working** (A's and B's replacements read vanilla, their wrappers still ran), presumably overridden by the compiled class copy.
  - So it is no merge tool for Ghost Mode yet: Ghost Mode has scope-based overrides with `default` lines, enum extensions and many `@replaceMethod`s. The merger is GUI only. Its `Tools\WSCompiler\WSCompiler.exe` is a separate command-line compiler (`compile`/`check --scripts <dir> [--reference <dir|.ws|.rsblob>] --json`), no replacement for `wcc_lite` in our builds so far.
- **Consoles** accept only blobs: no loose scripts, no load order, no Script Merger ([mod.io guide](https://mod.io/g/the-witcher-3/r/what-does-the-remaster-mean-for-modding)). CDPR recommends shipping the loose `.ws` files next to the blob on PC for reference and merging (same source); the game still ignores them while the blob is there.

So write scripts so they work in a blob, and use `--loose` builds only for experiments.

### Scope-based overrides (5.0)

Re-declare an existing class (or state) in a new file with **exactly its vanilla header**, and list only what to add or change. The game merges it into the vanilla class. **Verified** (pilot slice 2):

```ws
// Header copied from vanilla: "statemachine class W3PlayerWitcher extends CR4Player".
statemachine class W3PlayerWitcher extends CR4Player
{
	// New field and new method.
	var gmScopeOverrideCalls : int;

	public function GMScopeAdded() : string
	{
		return "OK";
	}

	// Override an existing method: replaces the vanilla body.
	public function GetCannotUseUndying() : bool
	{
		gmScopeOverrideCalls += 1;
		return cannotUseUndyingSkill;
	}

	// Change an existing default value (vanilla: 0.5f).
	default _HoldBeforeOpenRadialMenuTime = 0.51f;
}

// Enum extension: add members to a vanilla enum.
enum EEffectType
{
	EET_GMPilotEffect
}
```

Rules:

- Defaults of **behaviour-tree task definitions** (`...Def` classes) can be changed the same way, also for fields they inherit: `class CBTTaskAttackDef extends CBTTaskPlayAnimationEventDecoratorDef { default xmlStaminaCostName = 'light_action_stamina_cost'; }` gives every tree's attack task that cost unless the tree sets its own (trees store only non-default values). **Verified** (STAM-08). Abstract classes keep `abstract` in the header. To see which trees use a task or set one of its properties, extract the game's 389 `.w2behtree` files with `tools/unbundle.py` (base game and DLC bundles) and search their bytes for the `...Def` class or the property name (AI slice B1: no tree uses `CBTTaskReaction` or sets `useXMLTauntChance`; only 29 trees have a dodge task, so a monster without one never reads its dodge chances). Each `default` line of a block carries `//modSigns` too (`check_modsigns.py` lists unmarked ones).
- **A mod declares a class's scope-based override block once**: a second block for the same class, in another file, fails to compile ("Class 'W3GameParams' is already defined in current compilation unit", **verified**). Add further `default` lines to the existing block, each tagged with its feature (`W3GameParams`'s is in `stamina/staminaCosts.ws`).
- `import` classes can be overridden the same way, header included: `import class W3GameParams extends CObject { default HEAVY_STRIKE_COST_MULTIPLIER = 1.25; }` changes the constant (**verified**, STAM-03).
- The header must match the vanilla declaration: the same `statemachine`, `abstract` and `extends`. Otherwise: "Base class mismatch. Class 'W3PlayerWitcher' specifies no base but its previous definition uses 'CR4Player'", or "Previous definition of 'W3PlayerWitcher' is a state machine".
- An overriding method must keep the vanilla kind and signature: event stays event, latent stays latent, same return type. Timer and `final` functions cannot be overridden. The compiler names the mismatch.
- New enum members **must not have explicit values**: `wcc_lite` refuses them in an enum extension ("has an explicit value, that is forbidden for new enumerators defined in enum extensions (mods) to prevent conflicts"). Their numbers come after the vanilla members, and **each blob numbers its members as if it were alone**: two blob mods that add members to the same enum get the same numbers (**verified** 2026-11-13, `ETutorialHintPositionType`), and the number is compiled into the blob's code (a third mod declaring both members read 6 and 7 in its own code while `modPrbD`'s code still read 6).
- **At load the game builds one merged enum by name** (**verified** 2026-11-14, `EEffectType`): every mod's extension members are appended to the vanilla ones, a name already present is not added again, and **class `default` values are resolved by name against this merged enum**, while code literals keep each blob's compiled numbers. So when a second mod extends the same enum, the mod whose names are appended second gets merged numbers that differ from its compiled ones. A probe adding one member, 19 or 30 (sorting before or after `modGhostMode`, with or without a `mods.settings` entry) was appended first each time. Ghost Mode's effect classes (`default effectType = EET_GM...`) then got the merged numbers (192 and up) while its code asked for 173 and up: **every Ghost Mode effect type stopped working** (sign, Whirl and Rend cooldowns, Undying, Invigoration, Prolongation, Phantom Weapon, the Dimeritium bomb: 23 regression failures). Placeholder members to shift the numbers do not help: they are appended as names of their own. Effects in a save are unaffected either way: an effect's type is a `const` class default, not saved, so a loaded effect takes its number from the class (verified on the test-only slot: a probe effect saved as 191 came back as 192 after the probe gained a member).
- **What does work: a mod that extends the same enum declares the other mod's members first, by the same names and in the same order, then its own** (**verified** 2026-11-14: a probe declaring Ghost Mode's 18 effect type names and then its own member: Ghost Mode kept 173 to 190, the probe's effect worked at 191, the regression passed in both trees). With the full list in every blob, either load order works (`enum_sync.py`, below). The lists must stay in step: a member Ghost Mode adds later shifts the other mod's own member. **So any other mod that adds `EEffectType` members breaks Ghost Mode's effects unless it mirrors Ghost Mode's list** (or Ghost Mode mirrors its list): Preparations mirrors Ghost Mode's list this way (owner, 2026-11-14; TrianglePreparations `docs/port-plan.md`), Friendly Meditation adds none. When Ghost Mode adds an effect type, append it at the end of `gmEffectTypes.ws`, never in between or renamed, and update Preparations' copy.
- **`tools/enum_sync.py` does the mirroring on compiled blobs** ([tools.md](tools.md#build-and-game)): it gives every installed blob that extends an enum the full member list (all mods' members, in load order) and renumbers that blob's enum literals to match, without decompiling. Enum constants compile to plain `ByteConst`/`ShortConst`/`IntConst` literals with no type, so it infers each literal's type from the vanilla declarations; on Ghost Mode's blob every one of its 6,214 enum literals gets a type matching its value, and Ghost Mode patched behind a one-member probe equals, function for function, Ghost Mode compiled by `wcc_lite` with that member declared first (only source line numbers differ). **Verified in game** 2026-11-14, Ghost Mode with two one-member probes (`mod0PrbSyn`, `mod0PrbSyn2`, loading before it): with the list ordered probes first (Ghost Mode renumbered 173–190 → 175–192) and ordered Ghost Mode first (the probes renumbered to 191 and 192 although they load first), both probes' effects worked at their new numbers and the regression passed in both trees each time. So when every blob declares the same full list, load order no longer matters. Limits: code that tests a range of its own members (Ghost Mode's `GMIsModEffectType`: `> EET_EffectTypesSize && <= GMLastEffectType()`) also covers another mod's members placed before its own; explicit numbers (`(EEffectType)173`) are not renumbered (reported).
- States are re-declared with their vanilla header too, e.g. `state CombatFists in W3PlayerWitcher extends Combat { ... }` (compiles; not yet tested in game).
- **A scope-based override and a `@wrapMethod` of the same method, in one mod, both apply** (**verified**: `W3Effect_AutoStaminaRegen.OnUpdate`, then scope-overridden for STAM-04 and wrapped for STAM-07 and STAM-08). The same holds for `@replaceMethod` and `@wrapMethod` (**verified**, `gmtest_annotations`: the replaced `OnUpdate` recomputes the regen value and the wrapper still starts the heartbeat). So one feature can replace a method another feature wraps.
- If several mods override the same function or enum, the mod with the higher priority wins (community source; unverified here).

### Annotations

Annotations (added in patch 4.04, extended in 5.0) are declared outside any class, in a new file:

```ws
// Add a field to an existing class.
@addField(CR4Player)
public var gmPilotSpawns : int;

// Add a method to an existing class.
@addMethod(CR4Player)
function GMPilotSpawns() : int
{
	return gmPilotSpawns;
}

// Wrap an existing method: runs instead of it, and must call wrappedMethod(...)
// to run the original (and any other mods' wrappers).
@wrapMethod(CR4Player)
function OnSpawned(spawnData : SEntitySpawnData)
{
	wrappedMethod(spawnData);
	gmPilotSpawns += 1;
}

// Wrap a state's function: address the state by its internal class name,
// <state machine class>State<state name>. Inside, "parent" is the state machine.
@wrapMethod(CR4PlayerStateExploration)
function OnEnterState( prevStateName : name )
{
	parent.GMPilotCount('state');
	wrappedMethod(prevStateName);
}

// Replace a class method entirely.
@replaceMethod(CR4Player)
function GetSubmergeDepth() : float
{
	return submergeDepth;
}

// Replace a global function: no parentheses after the annotation.
@replaceMethod
function IsAutohealEnabled() : bool
{
	...
}
```

All of these are **verified** (pilot slices 1–2): `@addField`, `@addMethod`, `@wrapMethod` on an event and on a state event, `@replaceMethod` on a class method and on a global function.

Rules (from testing and the compiler's messages in `witcher3.exe`):

- **One `@replaceMethod` per function in the whole mod:** a second one, in another file, fails to compile ("@replaceMethod duplicate found for 'PlayerAimingStateAiming::SloMo'", MUT-11): add the change to the existing replacement (`grep -rn "function <name>"` first).
- **A wrapper calls `wrappedMethod` once:** a second call in the same body does not compile ("Could not find function 'wrappedMethod'", SKL).
- **WitcherScript has no string-to-name conversion** (`StringToName` does not exist), and a struct member cannot be read from a function's result (`GetMutation(m).progress`: "Parent scope does not come from variable"): assign the result to a local first.
- **Custom XML attributes read as names must end in `_name`** (`skill_name`, `def_name`, `ability_name`): `GetCustomNodeAttributeValueName` returns nothing for an attribute called `ability` (**verified**, SKL). A DLC's XML can add its own `<skill_definition>` block to `<custom><skills>` and scripts read it (**verified**, SKL).
- **A subclass override and wrappers of the base method combine:** a scope-based override of a method the class inherits (`W3PlayerAbilityManager.GetStaminaActionCost`, defined in `W3AbilityManager`) runs for that class, and its `super` call runs the base definition with every `@wrapMethod` of it; returning before `super` skips them all (**verified**, ALCH audit F4).
- **Moving vanilla lines inside a replaced body confuses `check_modsigns.py`:** its line diff can pair a moved block's braces with vanilla's and report an unmarked `}`; put the moved code in an `@addMethod` helper called from one marked line (ALCH audit F16, `GMLogCombatDamage`).
- **A behaviour-tree task created by script crashes the game when its code runs** (AI slice B3: `new CBTTaskCastQuen in theGame`, then its `ProcessAction`, which calls the native `GetActor()`; `...Def` objects created by script are safe). Put the logic a test needs in a global function the task calls (`GMNpcQuenStagger`) and test that.
- **A test wrapper can stack on another feature's `@replaceMethod` of a private function** (AI slice B1: probes on `CBTTaskDodge.CheckCounter` and `CBTTaskPerformParry.TryToParry`, replaced by STAM-08), and it reads the task's private fields (the chances it rolled).
- **A wrapper can stack on a replaced method:** `@replaceMethod(CR4Player) PerformParryCheck` plus a `@wrapMethod` on the subclass override that calls it via `super` both run (STAM-03).
- **A wrapper on a state's `entry` function compiles but never runs** (STAM-02: `W3PlayerWitcherStateCombatSword.PerformSpecialAttackLight`). Wrap the event or function that calls it instead. A `@replaceMethod` of one does run (declared as a plain `function`, without `entry`): `W3VehicleCombatManagerStateCastSign.StartCastingSign`, replaced with its `Sleep` loop, ran when the state called it.
- `@wrapMethod` works on `final` and `private` methods (**verified**, STAM-05: `W3PlayerWitcher.CalculatedArmorStaminaRegenBonus`, `CInventoryComponent.GetItemTooltipAttributes`; DEF-01: the private `W3DamageManagerProcessor.ProcessActionDamage`, whose wrapper reads the class's private fields), although a scope-based override cannot override a `final` one.
- The target class must exist, and the method must be **defined in that class**: "cannot wrap '%s' because it is a definition inherited from '%s'". Annotate the class that declares the method, not a subclass that inherits it.
- States: `@wrapMethod(CombatFists)` fails ("class 'CombatFists' is not defined"); use the internal name `W3PlayerWitcherStateCombatFists`.
- A wrapper must contain the `wrappedMethod` token and cannot be empty.
- A method added with `@addMethod` can itself be wrapped (e.g. by test code in another file). **Verified** (STAM-08). So can a global function the mod declares: a test probe wraps AI-12's `GMModifyHitSeverityFromDamage` with a class-less `@wrapMethod` (**verified**, AI slice B2). **A native (`import`) global function can be wrapped too** (**verified** 2026-11-14, TrianglePreparations PREP-REFILL): a class-less `@wrapMethod` of `GetLocStringByKeyExt` runs for script calls to it. This reaches a value a vanilla function builds in a local and hands straight to native Flash calls: set a flag around a wrapper of the caller and change the result only while it is set (Preparations adds charges to the alchemy list's names this way, without replacing `PopulateData`). Keep such a wrapper cheap: it runs for every script call of that function. Fields of `theGame` cannot be assigned through `theGame` directly ("Left hand side is const"): copy it into a local `CR4Game` first.
- **`@replaceMethod` of a timer function: declare it without `timer`** (`@replaceMethod(W3PlayerWitcher) function SpecialAttackLightSustainCost(dt : float, id : int)`); with the keyword the compiler stops at a syntax error. Timers added by name (`AddTimer('SpecialAttackLightSustainCost', ...)`) then run the replacement (**verified**, STAM-09). Scope-based overrides still cannot override timers.
- **Wrapping a latent function: declare the wrapper without `latent`** (`@wrapMethod(W3VehicleCombatManagerStateSwordAttack) function DoAttack()`); with the keyword the compiler stops at a syntax error. The wrapper runs, including the latent original (**verified**, STAM-03 horseback). Inside such a wrapper, `return wrappedMethod();` fails ("latent calls not allowed in return statement"): store the result in a local first.
- **Replacing a global quest function: declare it as a plain `function`**, without `latent` or `quest` (`@replaceMethod function ProcessMonsterHuntTrophyQuest(trophyName : name, dontTeleportHorse : bool)`; compiles, TRPH slice T3); the replacement still counts as a quest function (a call from a script fails with the quest-block error), so the quest blocks should still find it (open check: a contract's end in play). A **latent** quest function cannot be called from scripts ("Quest function '...' can only be called from as ScriptQuestBlock"): check it by compile and code, or in play; a non-latent one can (`HealthBarVisiblityQuest`, [Testing in game](#testing-in-game)).
- **Replacing a latent function: declare the replacement without `latent` too** (`@replaceMethod(W3YrdenEntity) function Place(...)`): it compiles, keeps its `Sleep` calls and runs latent (**verified** in play for Yrden's `Place`, SKL; compiles only for `CBTTaskWraithDrainDance.Main` and `BTTaskManageDjinnRage.Main`, ALCH-14 and ALCH-15, not yet run in game).
- **`@replaceMethod` of an event: declare it as a `function`, without a return type** (`@replaceMethod(W3Effect_AutoStaminaRegen) function OnUpdate(dt : float)`); with `event` the compiler stops ("unexpected TOKEN_EVENT, expecting TOKEN_FUNCTION"), and an explicit `: bool` is refused too ("Event function ... should not have an explicit return type. It is implicitly always bool"); the body's `return true;` and `return false;` stay. The replacement runs (**verified**, STAM-04). Wrappers of events are declared the same way.
- **`@replaceMethod` works on a state's function**, addressed by the state's internal class name like a wrapper: `@replaceMethod(W3SignEntityStateChanneling) function Update() : bool` (**verified**, STAM-03 channels).
- **A wrapper of an event cannot use a bare `return;`** ("Unable to convert from 'void' to 'Bool'"): put the code after `wrappedMethod` in an `if` block instead (**verified**).
- **Annotated functions take no access modifier**: `@replaceMethod(...) protected function SetEffectValue()` is a syntax error ("unexpected TOKEN_PROTECTED"); drop `protected`/`private`/`public`.
- **`@replaceMethod` cannot replace an inherited definition**: "@replaceMethod cannot replace 'CBTTaskAttack::GetStats' because it is a definition inherited from 'CBTTaskPlayAnimationEventDecorator'". Use a scope-based override of the subclass for that (STAM-08).
- **A wrapper may call `wrappedMethod` only once**: a second call (e.g. one in an early-return branch and one at the end) fails to compile with "Could not find function 'wrappedMethod'" at the second call (**verified**). Compute what the branches need, call `wrappedMethod` once, then branch on the result. A wrapper must contain the call (it does not compile without it, as the REDkit wiki says), but a branch may return before reaching it. Not documented by CDPR; the error suggests the compiler resolves the identifier `wrappedMethod` to the wrapped method only once.
- **Several `@wrapMethod`s of one method all run**, also from different files: each wraps the next (**verified**: a second wrapper of `W3AbilityManager.GetStaminaActionCost` ran once per call, and STAM-03's wrapper still applied its cost). So each feature wraps what it needs, even a method another feature already wraps; it need not hook into the other feature's wrapper. (STAM-07's calls still sit in STAM-08's `DrainStamina` and regen wrappers, from before this was known.)
- `@addMethod` can add a **timer function** (`@addMethod(W3PlayerWitcher) timer function GMCrushingChainEnded(dt : float, id : int)`), started by name with `AddTimer` (**verified**, SKL-04).
- `@addMethod` can add an **event** to a class (`@addMethod(W3VehicleCombatManager) event OnAttack(action : SInputAction) {}`); a state of that class that defines the event still handles it (**verified**, test code for STAM-03 horseback).
- `@replaceMethod` cannot replace native functions, native class functions or imports (`import function ...` in the vanilla scripts).
- Wrapping a **global** function: `@wrapMethod` without a class (e.g. on `EffectTypeToName`) is **verified** (STAM-01).
- Wrapping **native** functions (`import` functions in the vanilla scripts) works only from a blob ([mod.io guide](https://mod.io/g/the-witcher-3/r/what-does-the-remaster-mean-for-modding); the executable also says "cannot wrap '%s' because it is native (only allowed in modio mods)"). **Verified** from a blob (2026-11-13: a `@wrapMethod(CPlayer)` of the native `GetEnemyUpscaling` ran). The wrapper goes on the class that declares the import (`CPlayer`, not `CR4Player`: "cannot wrap ... because it is a definition inherited").. **Alarm:** a loose-script version could not do it, and there is probably no loose equivalent, so do not wrap a native function without the project owner's agreement; `tools/check_modsigns.py` flags any `@wrapMethod` of a native function.

### Adding effect types

New buffs and debuffs (cooldowns, potion effects, ...) need a new `EEffectType` member, an effect class and registration. **Verified** (STAM-01):

- Add the members with an **enum extension** in `scripts/local/gm/effects/gmEffectTypes.ws`, and keep `GMLastEffectType()` pointing at the last one.
- **Pitfall:** mod enum members come after the vanilla `EET_EffectTypesSize`, but `W3GameEffectManager.Initialize` sizes its effect array to `EET_EffectTypesSize`. `gmEffectRegistration.ws` wraps `Initialize` and grows the array; without that, the new effects index past its end. Vanilla loops up to `EET_EffectTypesSize` (immunities, Quen) simply skip mod effects.
- Register each type in `gmEffectRegistration.ws`: create the object in the wrapped `W3GameEffectManager.HACK_NO_MEMORY_TO_COMPILE_CacheEffect_Part1`, and map name and type in the wrapped global functions `HACK_NO_MEMORY_TO_COMPILE_EffectNameToType_Part1` and `EffectTypeToName`.
- An effect works without XML (5.x's own `EET_OverloadCooldown` has none): it then has no HUD icon or label. Override `CalculateDuration` to set the duration in script.
- Effect names follow the vanilla pattern `<Name>Effect`, with the `GM` prefix: `GMAardCooldownEffect`.
- **Effect abilities by level** (an item or bomb naming `<effect>_Level2` as its effect, as vanilla's `SilverDustEffect_Level2`): the ability's name must start with the effect's name and `_` (`GMDimeritiumEffect_Level2`), the `<effect>` entry in `gm_effects.xml` makes the name valid (`IsEffectNameValid` compares the part before `_`), and the wrapped `EffectNameToType_Part1` must map the suffixed name too, returning it as the ability name: vanilla splits the name before its switch, the wrapper's switch sees it whole (**verified**, ALCH-15).
- **A vanilla effect class cannot get another base class** (a scope-based override must repeat the vanilla `extends`). To turn one into, say, a damage-over-time effect, add a new effect type with its own class (MUT-10: `EET_GMMutation5`, `W3GMEffect_Mutation5 extends W3DamageOverTimeEffect`, for legacy's Mutated Skin) and stop the vanilla type from being added. A damage-over-time effect needs a damage attribute (`DirectDamage`) in its ability, even if the script sets the value (**verified**).
- **The `player_had_quen` fact** (5.x) makes `InternalAddEffect` deal 0.1 s of a new damage-over-time effect on Geralt and drop it; Ghost Mode no longer sets the fact and removes it on spawn (SKL-11). A DoT on Geralt that vanishes at once in a test points to it.

### Choosing a technique

| Change | Use |
|---|---|
| Add behaviour before or after a vanilla method (adjust arguments or the return value, add side effects) | `@wrapMethod`. Several mods can wrap the same method, so it is the most compatible. Prefer it. |
| Change logic in the middle of a vanilla method, or remove some of it | `@replaceMethod` (see the rule below). Copy the **5.x** body (from `vanilla-5.x`), apply the change, mark the changed lines with `//modSigns`. Only one mod's version can win, and CDPR updates to that method must be merged by hand, so keep replaced methods few and small. Prefer a replacement over a wrapper that gets the same result indirectly (e.g. by changing state around the call): the code then says what it does. |
| Change a global function | `@replaceMethod` (scope-based overrides cover classes and states) |
| Change a value a vanilla UI function puts into a flash object (character panel lines, ...) | `@wrapMethod` the function, let it build the object, then overwrite the member (`statObject.SetMemberFlashString("value", ...)`) |
| New fields and methods on a vanilla class | `@addField`/`@addMethod` |
| Changed `default` values on a vanilla class (also `import` classes such as `W3GameParams`, and behaviour-tree `...Def` classes) | A scope-based override block holding only the `default` lines |
| Override, in a vanilla class, a method it inherits but does not define itself | A scope-based override block (`@replaceMethod` refuses inherited definitions) |
| New effect types, item categories and other enum members | Enum extension |
| New classes, structs and global functions | Declare them in a new file |

**Replace with `@replaceMethod`, not with a scope-based override** (project owner, 2026-10-04): a function the vanilla class defines is replaced with `@replaceMethod`, even where a scope-based override block exists for the same class; scope-based overrides are kept for what only they can do: changed `default` values and overrides of inherited methods (enum members are an enum extension). The annotation states what the code does, and every replaced function reads the same way. A class can have both: a scope-based override, `@addMethod`s and `@replaceMethod`s on one class all apply, also from different files (**verified**, `gmtest_annotations` on `W3GameParams`).

Prefer **one file per vanilla class or system** that Ghost Mode changes, holding the scope-based override block and any annotations for it, each tagged with feature IDs. Shipping a whole edited copy of a vanilla script still works (in a blob it acts as an override of everything in the file), but it brings back the merge problem for no benefit; list only the changed members instead.

### WitcherScript rules learned along the way

- **Fields cannot be assigned through `thePlayer` or a function's return value**: `thePlayer.gmCounter += 1` fails with "Expected type 'Int32' to be assignable", `thePlayer.gmField = 1` with "Left hand side is const", `GetWitcherPlayer().gmField = 1` with "L-value required". Reading works. Assign through a local variable holding the object (`w = GetWitcherPlayer(); w.gmField = 1;`, **verified**, ITEM's tests), or give the class a method (`@addMethod`) and call that.
- Fields default to private; declare fields that other code reads as `public`.
- **`name` is a type keyword**: a parameter called `name` fails to compile ("unexpected TOKEN_TYPE_NAME"); call it something else. So is `set` ("unexpected TOKEN_SET"), `enter` ("unexpected TOKEN_ENTER"), `saved` ("unexpected TOKEN_SAVED", as a variable name) and `def` ("unexpected TOKEN_DEF", as a variable name).
- **An entity handle reads as null right after `Destroy()`**, in the same function: compute anything that tests the handle (`ent && ...`) before destroying it (**verified**, XBOW fix slice T).
- **A cast cannot follow `!` directly**: `if(!(CActor)x.attacker || ...)` is a syntax error ("unexpected TOKEN_CLASS_TYPE"); assign the cast to a local first.
- **Backslashes in strings are literal** (`"dlc\bob\data"` as in vanilla's own paths), but avoid a backslash right before the closing quote.
- **A short-lived flag needs no timer:** store a deadline (`theGame.GetEngineTimeAsSeconds() + 3.0`) and compare it when read (DEF-07's countered flag); not saved, so nothing survives a load.
- **Exec functions cannot be called from scripts** ("Cannot call exec function ... from scripts instead of the console"). Put shared test code in a plain function and make the exec function a one-line wrapper (`exec function gmtest_stam07() { GMTest_stam07(); }`), as `gmtest_regress()` does.
- **A struct field cannot be read straight off a function's return value**: `GetAttr(...).valueAdditive` fails with "Cannot access struct property ... Parent scope does not come from variable". Assign the result to a local first.
- **`import const` struct fields can be set on a local variable.** `SInputAction` declares its fields `import const var`, yet `action.value = 1;` compiles and works, so a script can build an input action and call an input event with it (see [Input simulation](game-automation.md#input-simulation)). Calling another object's event directly (`thePlayer.GetInputHandler().OnCastSign(action)`) works too.
- **Wrap where a state is left, not where it "ends", when every exit matters.** A sign can leave its casting state through `OnEnded` or `OnSignAborted` (e.g. `DrainStamina` aborts the current sign at 0 stamina); a wrapper on one of them misses the other. A wrapper on the state's `OnLeaveState` sees all exits. If the state has no `OnLeaveState` of its own, wrap its base state's and filter on `parent` (STAM-01, Igni).
- **A string cannot become a `name`** ("Unable to convert from 'String' to 'CName'", also with a `(name)` cast): code that needs names built from parts looks them up in a generated table (`tools/gen_test_dummy.py`).
- **One very large function exhausts the script compiler's memory** ("memory exhausted, near ..."): split generated code into several functions (vanilla's `HACK_NO_MEMORY_TO_COMPILE_*` functions do the same).
- **Reading an ability's value from the definitions** (`GetAbilityAttributeValue`): read the part its XML type sets (`valueAdditive` for `add`, `valueMultiplicative` for `mult`). For `base`, vanilla often adds a `mult` node of 1 next to it (`magic_s3`'s `charge_count`), which an `extend` keeps: read it as the game does, `CalculateAttributeValue` (base × mult + add), or `valueBase` when there is no multiplier; summing the parts counts the 1 (SKL audit F4, `GMTest_skl_values`).
- **Geralt's `GetAttributeValue('<resistance or spell_power>')` reads -9999 (mult 100)** on the test save, also through `autoattr`: read resistances with `GetResistValue(CDS_..., points, percents)` and sign intensity with `GetPowerStatValue(CPS_SpellPower)` (ARM-07). An effect's ability counts from the next frame: read it in a later exec call.
- **An NPC's stat attributes through the ability manager read -9999 (mult 100)** too: `CActor.GetAttributeValue` refuses "forbidden" attributes (`vitality`, `essence`, `attack_power`, the `*_resistance_perc` resistances, ...; `W3AbilityManager.CheckForbiddenAttribute`). Read them with `npc.GetCharacterStats().GetAttributeValue(name, emptyTags)`, which returns the sum of every ability's base, mult and add (AI-01's tests). An NPC's maximum health is `CalculateAttributeValue(vitality or essence)` × the `health_final_multiplier` attribute's additive part, which already includes the 1 (Hard: 2, from `difficulty_CommonHard`'s +1, legacy's since DIFF's slice D1; 5.x's 1.2).
- **An ability node without a `type`** (the weapons' `<SlashingDamage min="300" max="300"/>`) reads as base: `GetAbilityAttributeValue` puts it in `valueBase` (**verified**, AI-05's 213 weapon abilities). A generated table of expected values per ability (`tests/gmTestsAiData.ws`, `gen_ai.py`) checks hundreds of definitions in one regression check; keep each generated function to about 60 calls (compiler memory).
- **`Initialize` of a damage or attack action clears it first** (`W3DamageAction`'s base `Initialize` calls `Clear()`): the attacker, the hit-animation type and every other field set before it are lost, so set them after `Initialize` (legacy's leshen roots set both before it: dead lines, left out since the AI-C audit).
- **`RoundF` truncates** (5.x, seen in game, XP slice X3): 2.5, 2.6, 7.5, 14.8 and 29.6 give 2, 2, 7, 14 and 29; `RoundMath` rounds to the nearest. Legacy's kill experience uses `RoundF`, so its products are rounded down.
- **Pass a local, not a call, after `out` arguments:** `GMTestXp09Held(classic, newTree, wrong, GMTestXp09NewRule())` left the three `out` variables at 0 although the function set them; with the call's result stored in a local first and the local passed, they came back right (XP slice X5).
- **`SetMoney(0)` leaves 1 crown** (ECON slice E3): it removes the money and calls `AddAnItem('Crowns', 0)`, which adds one; empty an inventory's money with `RemoveMoney(GetMoney())`.
- **`reward` is a keyword** too (a function kind, as `exec`, `quest` and `storyscene`): a parameter called `reward` fails to compile ("unexpected TOKEN_REWARD").
- **An object handle is its own truth value, but cannot be compared with `NULL`**: `GMTestReport(res != NULL, ...)` fails to compile ("Unable to find suitable operator 'OperatorNotEqual' for given types (&handle:CResource, void)"); pass the handle where a `bool` is wanted (`GMTestReport(res, ...)`) or test it with `if(res)` (ECON slice E5).
- **Methods cannot be called on an array returned by a function** (`GetList().Contains(x)`: "Only arrays coming from variables can be modified"): store it in a variable first.
- Fields are not stored in saves unless declared `saved`. A `saved` field changes what saves contain, so record the save impact.
- **A loaded character keeps its stored maximum Vitality** (**verified**, XP slice X1): the abilities a character holds are saved by name and their attributes read live from the definitions (attack power and spell power changed at once), but the base stats' maximums are stored, and `W3AbilityManager.OnAbilityChanged` recomputes one (`UpdateStatMax`) only when an ability with that stat is added or removed. A level-20 Geralt saved with 5.x's level abilities loaded with 4,900 maximum Vitality although the DLC's give 4,450, until a Vitality ability changed. A change to a Vitality value Geralt already holds needs a recompute at load: XP-08's `@wrapMethod(W3PlayerWitcher) OnSpawned` (`xp/levelStats.ws`) calls `UpdateStatMax(BCS_Vitality)` when `spawnData.restored` and keeps the Vitality percentage. A test reads the live value by taking the abilities away and giving them back (`GMTestXpLevelParts`, `tests/gmTestsXp.ws`).

Unanswered questions about scripts (struct fields, state overrides) are tracked in [open-questions.md](open-questions.md).

### Other mods and vanilla code

- Never wrap or replace a method just to read a value: add a getter with `@addMethod` instead.
- **Sibling ports must combine with Ghost Mode as separate blobs, in any folder order** (TrianglePreparations, TriangleFriendlyMeditation): a method Ghost Mode replaces must not be changed by them, and the reverse (rules in [How the game loads mod scripts](#how-the-game-loads-mod-scripts)). Done for Preparations (owner's go-ahead 2026-11-13; **verified** 2026-11-14, both trees; TrianglePreparations `docs/ghost-mode-compatibility.md`): `CInventoryComponent.SingletonItemGetMaxAmmo` is a wrapper that adds the difference between Ghost Mode's bomb formula and 5.x's (`GMBombMaxAmmo(id, gmRules)` computes both; `GMTest_compat` in the regression checks the stack equals Ghost Mode's formula where the two differ); `CR4CharacterDupeMenu.OnSwapSkill` is a wrapper (colour gate before `wrappedMethod`, the slot emptying in a wrapper of `EquipSkill` armed only during the swap); STAM-10's exhaustion clear is a wrapper of `ApplyWitcherHouseBuffs` (called by `MeditationRestoring`'s last line), which Preparations' `MeditationRestoring` must keep calling. Keep these as wrappers. Before adding a `@replaceMethod` on a method in meditation, alchemy refill, oils, food, repair kits or skill equipping, check those repos' compatibility docs.
- Legacy Ghost Mode code calls helpers from Shared Imports and Community Patch – Base. Shared Imports is built into 5.x; check whether a Community Patch helper exists in 5.x before porting code that uses it. See [legacy-ghost-mode.md](legacy-ghost-mode.md#dependencies).

## XML and CSV

### Fine-grained XML overrides (5.0)

5.0 lets a DLC redefine existing XML entries, or individual fields of them, with an **`on_conflict`** attribute on the entry. **Verified** (pilot slice 3b). The 5.0 REDkit changelog writes it `onConflict`, but the game ignores that spelling; the attribute name in `witcher3.exe` is `on_conflict`.

| `on_conflict` | Effect | Verified |
|---|---|---|
| *(none)* | On a name vanilla defines: the DLC's entry is **ignored**, vanilla's kept, no error in the script log (the changelog says "error on redefinition") | yes, for items: ECON audit, `Jar of Honey` given whole at 777 without the attribute read 5.x's 50 (a `replace` control read its value); so every override needs the attribute. `tools/dlc_conflicts.py` (also run by `gen_econ.py --verify`) lists any DLC entry without it on a name 5.x defines (ECON audit F1) |
| `extend` | The entry's sub-nodes listed in the DLC replace the matching vanilla ones; all other sub-nodes are kept | yes: `sword_s1` with only `stamina_cost_per_sec` changed that value and kept `focus_cost_per_sec_initial`, `cost_reduction` and `stamina_delay` |
| `replace` | The DLC's entry replaces the vanilla one completely; sub-nodes it does not list are gone | yes: `sword_s2` with only `stamina_cost_per_sec` lost its other attributes (they read 0) |

**New Game+:** the `*_plus` siblings of definition folders (`abilities_plus/`, `items_plus/`, ...) are the New Game+ variants. Make every change in the regular folder, and the corresponding change in the `*_plus` counterpart: numbers scaled the way vanilla scales them from NG to NG+ (GM NG+ = vanilla NG+ × GM NG ÷ vanilla NG; edge cases in [feature-mapping.md](feature-mapping.md#ng-numbers)), everything else the same. NG+ is neither balanced nor tested (see [feature-mapping.md](feature-mapping.md#new-game-carried-over-and-scaled-not-balanced-or-tested)). In the in-game check, test the regular game only. Whether one DLC override also covers the NG+ definition of the same entry is an [open question](open-questions.md).

This is how Ghost Mode's XML changes are ported: Ghost Mode's DLC contains only the entries it changes, with `on_conflict="extend"` and only the changed sub-nodes, instead of a full copy of files like `geralt_skills.xml`. Use `replace` only when Ghost Mode removes sub-nodes or rewrites an entry wholesale. Entries Ghost Mode adds are plain new entries (no attribute).

```xml
<?xml version="1.0" encoding="UTF-8"?>
<redxml>
  <definitions>
    <abilities>
      <!-- SKL-12: Ghost Mode value for a sword skill -->
      <ability name="sword_s1" on_conflict="extend">
        <stamina_cost_per_sec type="add" min="78" />
      </ability>
    </abilities>
  </definitions>
</redxml>
```

Each of the DLC's XML files (or folders) is registered with a `CR4DefinitionsDLCMounter` in its `.reddlc` file (see [DLC and mounters](#dlc-and-mounters)). XML files are UTF-8 with BOM, like the 5.0 originals.

A DLC's definitions XML can also add to the `<custom>` sections that sit next to `<definitions>`, e.g. new `<effects>` and `<effect_icons>` entries for mod effects (**verified**, STAM-01: icons, HUD flag and labels of the sign cooldowns come from `dlc\dlcghostmode\data\gameplay\abilities\gm_effects.xml`). Ghost Mode's DLC mounts the whole `dlc\dlcghostmode\data\gameplay\abilities\` and `items\` folders (and their `_plus` twins); add a mounter per folder as other definition types are ported (`make_reddlc.py --xml` once per folder). New items, their abilities and new alchemy recipes (`<custom><alchemy_recipes>`) load from the DLC's `items\` folder: the alchemy manager finds the recipe and brews it (**verified**, MUT-12's Mutation Catalyst). A new cooked-item type works too: FOOD-07's cooking recipes use `cookedItemType="edibles"`, made known by an enum extension of `EAlchemyCookedItemType` and wrappers of the three type functions, and the alchemy menu shows them as their own group (**verified**). In tests, `W3AlchemyManager.Init()` loads only the recipes Geralt knows: pass the names (`Init(names)`) or read `GetCustomDefinition('alchemy_recipes')`. New crafting schematics (`<custom><crafting_schematics>`) load the same way: `getCraftingSchematicFromName` reads them and `AddCraftingSchematic` teaches them (**verified**, ARM-12). A schematic cannot be overridden: the crafting manager reads every `<schematic>` entry of a name, so a DLC copy would add a second one; give a changed schematic a new name. A DLC can also add a `<custom>` node of its own name, which scripts read with `GetCustomDefinition('<name>')` (**verified**, ENCH-02: `gm_enchantment_schematics`); the enchanter's schematics, which keep their names, are overridden that way, with the three readers replaced to look there first. An item's `localisation_key_name` is a key for the string tables (`GetItemLocalizedNameByUniqueID` returns the key).

**New Game+:** NG+ reads its definitions from `*_plus` folders, and a DLC adds its own with a `CR4DefinitionsNGPlusDLCMounter` (`make_reddlc.py --xml-ngplus`), as vanilla DLCs mount their `abilities_plus\` and `items_plus\` folders next to `abilities\` and `items\` (same file names). Ghost Mode's DLC mounts `abilities_plus\` with copies of its `abilities\` files that `tools/gen_ngplus.py` generates with the [NG+ rule](feature-mapping.md#ng-numbers) (a plain new entry whose name 5.x defines only in its NG+ files, such as several of DIFF-02's variants, gets `on_conflict="replace"` in the copy); re-run it after changing a file in `abilities\` (`--check` fails when a copy is out of date). In a regular game the NG+ copies are not read (**verified**: with a build whose NG+ copy gave the wolf a different stamina regen, the regular game used the `abilities\` value). NG+ itself is not tested.

**A regular game does not read a DLC's `_plus` folders at all** (**verified**, ARM-12): names defined only in `items_plus` (the 16 `Base Kaer Morhen … _Stats` abilities, the `NGP Kaer Morhen *` items) read as unknown on the test save (0 attributes, category `None`). New Game+-only data can therefore be checked offline only (`gen_*.py --verify`, `dlc_conflicts.py`), never from the test save.

**Abilities defined by the expansions' XML:** `extend` empties **Hearts of Stone's** (`dlc\ep1`) abilities: they lose every attribute and tag (**verified**: SKL-18, the perks `perk_13` to `perk_22`, `perk_22` lost its `GlobalPassiveBonus` tag and was never added to Geralt, `perk_19` was added without its crit chance; AI-A audit, the Caretaker's `q604_caretaker` and `q604_shades` and the NPC attack `attack_heavy_noparry` read 0 attributes). **Blood and Wine's** (`dlc\bob`) keep theirs: `BloodBuff`, `mon_sharley_base` and `mon_EP2_ffquicki` read their tags and every attribute with STAM-08's `extend` (**verified**; `BloodBuff` again in the DIFF audit: Essence regen 50, stamina regen 20 and its tag). No other DLC's abilities have been tried. Both fit DLCs loading in folder-name order (`bob`, `dlcghostmode`, `ep1`), unverified. `gmtest_ability_probe(<ability>, <tag>)` lists an ability's attributes as the game has them. Give a Hearts of Stone ability whole (`on_conflict="replace"` with its tags and every attribute it needs), and any other expansion's unless it was read in game after the `extend`. When only one feature's nodes of an ability are ported and the rest belongs to later features, give it whole as **5.x's entry with legacy's nodes for that feature's tags** (the tags legacy changed from 1.32; `gen_ai.py`'s `PART`, AI slice B1: the Wild Hunt's abilities with legacy's combat rolls and STAM-08's stamina values, their AI-15 stats 5.x's), rather than `extend` with repeated-tag ordering. Give every expansion ability whole; the AI-A audit's sweep of every `extend` in Ghost Mode's DLC against the definitions' homes in `vanilla-5.x` left none on a Hearts of Stone ability. **No name may be given whole (`replace`) twice in the DLC.** Several `extend` entries of one ability are allowed, and they apply together, each with its own nodes: **verified** for `ConGeralt`'s five entries in `gm_stats.xml` (OPT-02's resistances read 0 with the stamina regen of an earlier entry kept, `GMTest_opt02_resist`) and for `sword_s21` in `gm_defense.xml` (DEF-07's counter tag) and `gm_skill_trees.xml` (SKL's values), both halves measured on counters (SKL-03). The other doubled abilities (`attack_heavy`, `attack_heavy_special` and `attack_super_heavy` in `gm_damage.xml` and `gm_adrenaline.xml`; `sword_s1` in `gm_skills.xml` and `gm_skill_trees.xml`; `magic_s4` twice in `gm_skills.xml`) follow the same rule: **verified** by the regression's read-back of every entry of every doubled ability, plus one vanilla attribute no entry lists (`GMTest_data_extends`, both trees). Keep each tag in one of the entries: how two `extend`s that list the same tag combine is untested. When two of Ghost Mode's files both `replace` one ability, the regular game read one of them (`gm_trph.xml`'s `pig_contest_trophy_stats` over `gm_wgt.xml`'s, TRPH audit F1), by the load order, which is not a rule to rely on; each generator's `--verify` fails when a name it writes is defined twice in the DLC (hand-written files such as `gm_stats.xml` are not checked). `replace` is reliable: AI-A gives about 200 Hearts of Stone, Blood and Wine and free-DLC enemy and weapon abilities whole, and every one reads its values in game (**verified**, `GMTest_ai03`).

**Items** (`<item>` entries) take `on_conflict="replace"` given whole, from the base game's files and the expansions' and free DLCs' alike. **When `extend` is allowed for an item** (the project owner, 2026-11-01): for a change of the entry's own attributes (such as `price`) and of its tags only, on an item of the base game, Blood and Wine or a free DLC, in the regular `items` folder, when no other area writes the entry whole: a short entry `<item name="…" price="…" on_conflict="extend">` with a `<tags>` node that adds tags and removes those written `-tag` (ECON's `gen_econ.py`). Everything else stays `replace`, whole: Hearts of Stone's items (`extend` empties them), a change to a child block (`base_abilities`, `recycling_parts`, ...), NG+ entries (`items_plus`: an NG+ `extend` cannot be read in a regular game, so it is untested), and any entry another area already writes whole (that area's tool applies the other areas' fields to it through `item_layer.apply_item`). Write `</item>` on its own line: some tools read item entries line by line. Tools that read the DLC's items as the game does resolve an `extend` entry over 5.x's (`gen_arm_items.dlc_entries`, `item_layer.resolve_extend`). `replace` given whole is **verified** for all of them (ARM-05: `Lynx Armor`, Hearts of Stone's `EP1 Witcher Armor`, Blood and Wine's `q704 vampire silver sword` and the free DLC's `NGP Wolf Armor` read the DLC's tags with their abilities, category and slots kept). Item entries can hold nested `<item>` elements (inside `<variants>`), so tools must balance the tags when cutting an entry out. An item's tags are read from its definition, also for items a save already holds (verified, ARM-05: no re-acquiring for tag changes). An item with `ability_mode="OnMount"` has no attributes until it is equipped (`GetItemAttributeValue` reads 0 in the bag): read its abilities from the definition instead.

**An item's weight** (**verified**, WGT slices W1 and W2): `GetItemWeight` is the item's own `weight` attribute when it is above 0, else the sum of its abilities' `<weight>` nodes; the two are never added (Blood and Wine's Toussaint Crossbow 1, item 1.53 and ability 2.39, weighs 1.53). A weight node with a `max` above its `min` is rolled per copy (legacy's pig contest trophy, 5 to 10).

**`extend` on an item sets the entry's own attributes** (**verified**, ECON slice E1, a throwaway build): `<item name="Iron ore" price="7" on_conflict="extend"/>` sets the price and keeps everything else (category, weight, texts, icon, templates, tags, abilities), for items of the base game (`Iron ore`), Blood and Wine (`Dye Black`) and the free DLCs (`dlc1`'s and `dlc14`'s saddles, `dlc10`'s Wolf School schematic). A `<tags>` node in an `extend` entry **adds** its tags to the item's, and a tag written with a leading `-` is **removed** (`<tags>-mod_alchemy, mod_junk</tags>` on `Dwarven spirit`: `AlchemyIngredient, StrongAlcohol, mod_junk`). **Pitfall: `extend` empties a Hearts of Stone item** as it does Hearts of Stone's abilities (`Shani Flower 1` read price 0, category `default`, no tags, texts or weight): give those whole with `replace`. NG+ (`items_plus`) entries could not be tried: NG+ definitions are read only in an NG+ game, which no test save is (ECON slice E2), so NG+ entries are given whole. ECON's slice E2 ships 531 such `extend` entries, every one read back in game (`GMTest_econdata`, **verified**).

**Loot lists** (`<loot>`): a DLC entry with a vanilla list's name is merged into it: its entries are added, the vanilla list's own entries and quantity stay, also with `on_conflict="replace"` (**verified**, LOOT's DT1 probe on `Gwint Test`; vanilla's free Wolf DLC adds its maps to `_store__Hattori_Master_Blacksmith` this way). So a DLC cannot remove loot entries: lists Ghost Mode changes are whole-file overrides (`gen_loot.py`). New lists in a DLC load. A list queued with `AddItemsFromLootDefinition` gives at most **62 kinds** of items, the first eligible entries in list order; a merchant's restock from its entity's own lists is not limited (the Master Alchemist 185 kinds, the Hearts of Stone enchanter 120, both to the end of their lists; CRAFT and LOOT audit F6). The limit is native: the scripts only call imports.

**Repeated tags** (e.g. `ConGeralt` has three `<staminaRegen>` nodes: `add`, `base`, `mult`): `extend` replaces them **in order**: the first `<staminaRegen>` in the override replaces the first one in the vanilla entry, the second the second, and so on; the rest are kept (**verified**, STAM-04). So to change the Nth occurrence, list all occurrences up to it in vanilla order, copying the unchanged ones:

```xml
<ability name="ConGeralt" on_conflict="extend">
  <staminaRegen type="add" always_random="false" min="0" max="0" />     <!-- unchanged -->
  <staminaRegen type="base" always_random="false" min="1" max="1" />    <!-- unchanged -->
  <staminaRegen type="mult" always_random="false" min="0.15" max="0.15" />
</ability>
```

A single `<staminaRegen type="mult">` would have replaced the first node (the `add`) and left the vanilla `mult` in place.

From the [mod.io guide](https://mod.io/g/the-witcher-3/r/what-does-the-remaster-mean-for-modding) (unverified): `extend` removes a tag listed with a leading `-`; `on_conflict` works on `<Attitude>`, `<ability>`, `<item>`, `<item_extension>`, `<set>`, `<usable_item>`, `<res>` and `<reward>`; it does **not** work on `<alchemy_recipes>`, `<crafting_schematics>`, `<effects>`, `<effect_icons>`, `<mutations>`, `<skills>`, `<skill_slots>` and `<mutagen_slots>` (adding new entries, as `gm_effects.xml` does, is not overriding); `<card>` seems to take `replace` but not `extend`. **`<effect>` entries cannot be overridden** (**verified**, EFX-13): a DLC entry with a vanilla effect's name, plain or with `on_conflict="replace"`, is added after vanilla's in `GetCustomDefinition('effects')`, and `CBaseGameplayEffect.CacheSettings` reads only the first entry of its type, vanilla's (`gmtest_efx13_probe()` lists the entries of a name). `extend` sets an item's own attributes and adds or (with `-`) removes tags, but empties Hearts of Stone items (**verified**, ECON slice E1, above).

### CSV

Some CSVs can be mounted from a DLC (e.g. quest levels through `CR4QuestDLCMounter.questLevelsFilePath`). Whether a CSV mounted from Ghost Mode's own DLC overrides vanilla rows or only adds rows is **unverified**; for quest levels it would only add a table, which the journal reads after the others (below). Otherwise, ship a whole-file override: edit `master`'s copy of the file at its vanilla path under `modGhostMode/files/`, changing only Ghost Mode's rows; the build ships it because it differs from `vanilla-5.x`. `economy_tagmodifiers.csv` (the price factors) has no mounter and is overridden this way: since ECON's slice E1 the copy is legacy's file exactly, and the game reads its factors from the mod's bundle (**verified**: every merchant price and fee read moved to the new factors, `gmtest_econ_e1`). How the native code combines them is in [game-5.0-changes.md](game-5.0-changes.md#gameplay-systems-from-the-official-patch-notes) ("Prices").

**Quest levels** (**verified**, XP slice X2): the game keeps one table per loaded file in `CR4Game.questLevelsContainer` (paths in the private `questLevelsFilePaths`), the DLCs' first, each by its quest mounter (`bob`, `dlc3`, `dlc10`'s `th1009_quest_levels_copy.csv`, `dlc12`, `dlc15`, `ep1`), and the base game's `gameplay\globals\quest_levels.csv` last (`OnGameStarting`); the journal and the quest tracker read every table and keep the last row of a quest's name. A whole-file override in the mod's bundle replaces a DLC's table as well as the base game's (`gen_xp.py` writes the four XP-03 tables; read back by `GMTest_xpquestdata`). Reward files work the same way: the overrides of the expansions' and free DLCs' `rewards.xml` (`dlc\<name>\data\gameplay\rewards\rewards.xml`, mounted by `CR4RewardsDLCMounter`) are what `GetReward` reads (**verified**, all six files).

## DLC and mounters

A DLC is a folder under `dlc\<name>\` with a `.reddlc` file (a CR2W `CDLCDefinition`; `tools/cr2w_dump.py` reads it) that lists **mounters**. Mounters tell the engine where the DLC's files are and attach them to the game. They are the conflict-free way to add things to base-game content. Mounters relevant to Ghost Mode:

| Mounter | What it does | Possible Ghost Mode use |
|---|---|---|
| `CR4DefinitionsDLCMounter` | Loads a definitions XML | All XML overrides |
| `CR4EntityTemplateParamDLCMounter` | Adds parameters to entity templates at given paths | Adding abilities or stats to enemies without editing `.w2ent` files (e.g. the tournament contestants' `sq701_tournament_npcs` ability) |
| `CR4EntityTemplateSlotDLCMounter`, `CR4DefinitionsEntitieTemplatesDLCMounter` | Slots / entity template folders | If Ghost Mode needs new entities |
| `CR4JournalEntriesDLCMounter`, `CR4JournalDLCMounter` | Journal entries | Bestiary "use against" changes |
| `CR4RewardsDLCMounter` | Rewards XML | Quest reward changes |
| `CR4QuestDLCMounter` | Starts a quest; also takes scene voice tags and quest levels CSVs | Quest level changes |
| `CGameplayDLCMounterScripted` | Scriptable mounter | Script-side setup when the DLC mounts |

Full list: [REDkit wiki: DLC Mods](https://cdprojektred.atlassian.net/wiki/spaces/W3REDkit/pages/6328346/DLC+Mods). 5.0 added more ("e.g. the LoadingScreenDLCMounter", undocumented). `r4data\dlc\*\*.reddlc` in the REDkit install are working examples (`python tools/cr2w_dump.py "<REDkit>\r4data\dlc\dlc10\dlc10.reddlc"`).

On consoles, a definitions mounter may have to name single XML files instead of a folder, for both the regular and the NG+ mounter ([mod.io guide](https://mod.io/g/the-witcher-3/r/what-does-the-remaster-mean-for-modding), marked uncertain there; PC mounts folders, as Ghost Mode does).

Write `.reddlc` files with `tools/make_reddlc.py` (`--id`, one `--xml` per definitions file or folder; its `--selftest` rebuilds vanilla `dlc8.reddlc` byte for byte). It sets the DLC as hidden from the DLC menu and **not required by saves**, so removing the mod does not make saves unloadable. A DLC packed in a mod's bundle (under `<game>\mods\`) is found and enabled by the game (verified, pilot slice 3b: `IsDLCAvailable('dlc_ghostmode')` and `IsDLCEnabled` both true). REDkit can also create them in its editor.

## Binary resources

See [binary-files.md](binary-files.md). Before editing a `.w2ent`, check whether a mounter can do the same job. Edits that remain are made in the REDkit editor on the 5.x file (REDkit workspace: check out the file, edit, save).

**Legacy's entity edits are ported by generator, not by hand** (LOOT, AI-A; **verified** in game): the generator derives legacy's edits from `vanilla-1.32` → `legacy-GM` for the properties its feature owns, object by object (class and ordinal), and applies them to 5.x's file with `cr2w_patch.py`, so W3Edit's re-save noise is not carried over; `--verify` checks each file is 5.x's plus exactly those edits ([tools.md](tools.md): `gen_loot.py`, `gen_ai_ent.py`). Rules learned:

- **An edit addresses the class's Nth object in the file and in its compiled copy (`flatCompiledData`) alike.** Legacy's W3Edit re-saves sometimes changed a value in one copy only (a level in the entity object but not the compiled copy, or the reverse); the port sets both, and a verify must accept the twin.
- **Filter on the owned properties**, not whole objects: an entity's object also carries other features' properties and W3Edit's runtime noise (`currentLevel`, a re-saved `CCharacterStats`, the ability manager's stat arrays). Decode only the owned properties: other properties of 5.x's files do not always decode (`EntitySlot` arrays).
- **Several generators can edit one file:** the first (LOOT) applies its own edits and then the others' (`gen_loot.bin_expected`), the later one starts from the first one's output, and each tool's verify leaves the others' objects to them; both write identical bytes.
- **5.x already made some of legacy's edits** (the spiders' insectoid category): a value 5.x already has as legacy's is no edit; a value 5.x changed otherwise is a conflict to decide by hand.
- **Arrays get legacy's removals and additions on 5.x's list**, so 5.x's own entries stay; when 5.x rebuilt a file so that legacy's object has no counterpart, apply legacy's intent explicitly (AI's crowd succubi) and list it.
- **A header-only 5.x change** (CR2W version and build fields, as `sq209_cave_nekkers.w2comm`) lets a file take legacy's body with 5.x's header, rebuilt so every CRC is recomputed (legacy's W3Edit CRCs can be stale). Changing an import (another entity referenced) is beyond `cr2w_patch.py`'s edits on the command line (generators can call its `repoint_imports`).

**Cooked effects are edited by generator too** (the new tree's Muscle Memory and Strength Training glows, `tools/gen_sword_glows.py`): a recolored or new effect is a new entry in the template's `cookedEffects` (a renamed copy of a vanilla one, its buffer's imports pointed to new files under `dlc\dlcghostmode\fx\`), plus copies of the cooked particle system and material with their colors changed by same-size byte edits (`cr2w_patch.patch_bytes`); the game's files are read from the install's bundles, nothing is cooked. Facts about the cooked layout in [game-5.0-changes.md](game-5.0-changes.md#entity-effects-cooked). Such a template is a whole-file override (form 4): it must be regenerated when a game update changes the template, and another mod overriding the same template conflicts with it.

## Sound banks

A mod ships Wwise banks in `<mod>\content\soundspc.cache`, and scripts load and play them with `theSound.SoundLoadBank("<bank>.bnk", false)`, `theSound.SoundEvent("<event>")` and `theSound.SoundParameter("<game parameter>", value)`. **Verified** (STAM-07): the game loaded Ghost Mode's rebuilt heartbeat bank from the mod's cache and played it, with its game parameters and `game_state` muting working. Two conditions:

- **The bank must be built with Wwise 2023.1** (bank version 150; see [game-5.0-changes.md](game-5.0-changes.md#audio)). Legacy banks (version 88) have to be rebuilt; vgmstream (`vgmstream-cli -o out.wav <bank or .wem>`) decodes their audio to WAV, since no Wwise tool exports audio.
- **The cache must be format version 2**, written by `python tools/soundcache.py pack <out>\soundspc.cache <bank> ...` ([tools.md](tools.md#project-tools-tools)). Whether the game still reads legacy's version 1 caches is untested (they hold only version 88 banks anyway).

**Loading is asynchronous and counted:** `SoundLoadBank(bank, true)` loads in the background, so `SoundIsBankLoaded` turns true only in a later frame (check in a later exec call); a bank loaded several times (equipping a mutation loads its bank more than once) needs as many `SoundUnloadBank` calls before it reads unloaded (**verified**, MUT-01).

**Where things live:** the repository holds only the built banks, `modGhostMode/sound/*.bnk` on `master`; `tools/build_mod.py` packs them into the mod's `content\soundspc.cache`. The Wwise project, the decoded audio and the WAAPI scripts are kept locally, outside the repository, in a `TGM-audio` folder next to the checkouts (not in git; its README has the rebuild command). Legacy's banks stay recoverable from `legacy-GM` (`tools/soundcache.py extract`, then vgmstream).

**Building a bank without REDkit's editor:**

- Work in a copy of REDkit's audio project (`<REDkit>\assets\w3_audio`) **without** `Originals` (29 GB) and without the work units of the Actor-Mixer, Events, Interactive Music, SoundBanks, Dynamic Dialogue and Soundcaster hierarchies (keep each `Default Work Unit.wwu`); also remove the `Effects` lists from `Audio Devices\Default Work Unit.wwu`. The full project does not generate: it has 26,219 media items against the 200 the free licence allows, and its audio devices use the Mastering Suite, which needs its own licence. The trimmed project keeps the buses, state groups, switches, game parameters and conversion settings, so the bank's references resolve. Wwise IDs are hashes of the names (FNV-1 32-bit, lower case), so the bank refers to the game's own buses and states, e.g. `Gameplay Master Bus` or the `game_state` states.
- Script it through WAAPI: `WwiseConsole.exe waapi-server <project>.wproj --wamp-port <port>` (WwiseConsole is in `<Wwise>\Authoring\x64\Release\bin\`, where `<Wwise>` is the folder the Audiokinetic Launcher installed 2023.1.19.8928 into). Its HTTP endpoint does not start without admin rights (http.sys), so use WAMP over WebSocket; a stdlib-only client is about 60 lines. `ak.wwise.core.audio.import`, `object.create`, `object.set` (`@RTPC`, `@Effects`), `object.setReference` (`OutputBus`, by ID), `object.setStateGroups`, `object.setStateProperties` and `soundbank.setInclusions` cover a simple bank. WAAPI cannot set per-state values: add them to the saved work unit (`<CustomState ...><PropertyList><Property Name="Volume" Type="Real64" Value="-96"/></PropertyList></CustomState>`).
- Generate with `WwiseConsole.exe generate-soundbank <project>.wproj --bank <name> --platform Windows`. REDkit's project writes banks to `..\..\..\r4data\soundbanks\<platform>\`, outside the project folder: in a copy, set the SoundBank paths to `GeneratedSoundBanks\<platform>\` (`--output` sets only the external-sources path).
- **Curve shapes:** WAAPI and the work units call the bank's interpolation 1 (sine, constant-power fade in) `Log2` and 7 (reciprocal sine) `Exp2`; `Sine` and `SineRecip` are rejected. **dB curves** are stored as 10^(dB/20) − 1 below 0 dB and 1 − 10^(−dB/20) above, so a legacy bank's stored value converts back to the dB to author.

## Localization

**Verified** (pilot slice 4). A mod's strings ship as `content\<lang>.w3strings` next to its script blob and bundle; the game loads them without registration.

- **Source:** CSV files in the community encoder's format, `modGhostMode/localization/<table>/<lang>.csv` (the legacy layout; legacy Ghost Mode has the tables `modGhostMode` and `modGMTutorials`):

  ```
  ;meta[language=en]
  ; id      |key(hex)|key(str)| text
  2110992001|        |panel_ghost_mode|Ghost Mode
  ```

  Leave `key(hex)` empty; it is computed from `key(str)`.
- **Build:** `tools/build_mod.py` merges every table per language and encodes `<lang>.w3strings` with `tools/w3strings.py` (format version 164: UTF-8). The community w3strings encoder writes the legacy format (version 162, UTF-16) and is not used.
- **Lookup:** scripts find a string by key (`GetLocStringByKeyExt("panel_ghost_mode")`) or by id (`GetLocStringById(2110992001)`).
- **IDs:** Ghost Mode keeps its legacy IDs, **2110992000–2110992999** (the community encoder's ID space 992). They are inside the range REDkit allows for mods (10,000,000 to `0x7FFFFFFF - 1000`) and far above the vanilla IDs (97,959–1,482,499 in 5.0). New strings take the next free number in this range.
- **Overriding vanilla text:** a row with a vanilla string's id replaces that string. If the vanilla string has a key, repeat the key in the row too: lookups by key otherwise still find the vanilla text. (Legacy `modGMTutorials` rewrites vanilla tutorial strings this way.) Find a vanilla string's id and key by decoding the game's table: `python tools/w3strings.py decode "<game>\content\content0\en.w3strings" en.csv` (key names are not stored, only their hashes; `w3strings.key_hash()` computes one).
- **Languages:** one CSV per language (`en`, `pl`, `de`, ... as the game names its tables). What the game shows in a language for which the mod has no table is an [open question](open-questions.md).

## Options menu

**Verified** (pilot slice 5). Ghost Mode's settings appear under Options → Mods, defined by XML and read by scripts through the in-game config system.

- **Source:** `modGhostMode/menu/<file>.xml` (UTF-8 with BOM, like the game's own menu files). Format, as in legacy Ghost Mode's `modSignsConfig.xml`:

  ```xml
  <UserConfig>
  	<Group id="GMPilot" displayName="Mods.gm_pilot">
  		<VisibleVars>
  			<Var id="GMPilotToggle" displayName="gm_pilot_toggle" displayType="TOGGLE"/>
  		</VisibleVars>
  	</Group>
  </UserConfig>
  ```

  Other `displayType`s: `OPTIONS` (with an `<OptionsArray>`), `SLIDER;min;max;steps`, `SUBTLE_SEPARATOR`; groups can have a `<PresetsArray>`. The game's own files in `<game>\bin\config\r4game\user_config_matrix\pc\` are working examples.
- **Install:** the game reads every `*.xml` in `<game>\bin\config\r4game\user_config_matrix\pc\` (the folder comes from `MatrixPath` in `bin\config\r4game\ingameconfig.ini`). No list file needs editing; legacy `dx11filelist.txt` does not exist in 5.x. Menu files cannot live in the mod folder, so `tools/build_mod.py --install` copies them there and records them for removal on the next install.
- **Menu tree:** a group's `displayName` is a dotted path. `Mods.<name>` puts the group under the game's own Options → Mods entry (its label `panel_mods` is vanilla).
- **Labels** are string keys in Ghost Mode's string table: `panel_<segment>` for each path segment (`panel_gm_pilot`), `option_<displayName>` for a variable (`option_gm_pilot_toggle`), `preset_value_<name>` for option and preset values.
- **Reading a value:** `theGame.GetInGameConfigWrapper().GetVarValue('GMPilot', 'GMPilotToggle')` returns a string (`"true"`, `"2"`, ...). A variable that was never set returns `""`; a virtual `OPTIONS` variable (an id starting `Virtual_`, whose value is the option matching its entries' variables) returns `"-1"`, and `SetVarValue(..., "")` does not clear it: only a settings file without the value does (game closed). `GMOptionUnset` treats both as unset (DIFF-04, verified).
- **Ghost Mode's options** (OPT-01): add each option to `modGhostMode/menu/modGhostMode.xml` (legacy group and variable ids), give it a default in `GMOptionDefault` and an entry in `GMOptionList` (`scripts/local/gm/options/gmOptions.ws`), its label to the string tables, and read it with `GMGetOptionFloat(group, option)`, which falls back to the default while the option is empty. Unset options get their defaults when a save loads (**verified**).
- **Storage:** values are saved in `Documents\The Witcher 3\dx12user.settings`, one `[<group id>]` section per group. (`user.settings` is the legacy file; 5.x does not read it.)
- **Testing:** **`autoconfigset` saves into the player's real `dx12user.settings`**: set changed options back to their defaults (`GMOptionDefault`) after the test, or edit the file while the game is closed. `modAutomation`'s `autoconfig("<group id>")` lists a group's variables with labels, types, values and visibility, and `autoconfigset("<group id>", "<var id>", "<value>")` sets and saves one (see [game-automation.md](game-automation.md)). These check registration, labels and reading without opening the menu. A variable the menu XML does not declare cannot be set (`autoconfigset` answers "config var not found"). **The menu's change path without input** (DIFF-04): `ingamemenu()`, then a test exec that sets the value and calls the open `CR4IngameMenu`'s `OnOptionValueChanged` (the menu is the root menu's last child), as its Flash does, then `game.py resume`: closing runs the menu's `OnClosingMenu`, `SaveChangedSettings` and Ghost Mode's change hooks, and saves the settings file. A **preset** goes the same way through the menu's `OnPresetApplied(groupId, index)` (it calls `ApplyGroupPreset`; **verified** with the pause menu open on its first page, DIFF-04 slice D5b); a wrapper of `OnPresetApplied` is where a group reacts to its presets. A preset's entries name the virtual option's backing variable (`GMScaling`), which `GetVarValue` reads as `""` (it is not a declared variable): read the virtual one (`Virtual_GMScaling`) instead. **A new choice appended to a virtual option** (DIFF-10's value 6 after legacy's 0 to 5) is saved and read back after a relaunch; a stored value that matches no entry of the menu XML reads as unset (`"-1"`), so the option takes its default at the next load (seen on a throwaway build without the entry: "6" came back as "3"). An option that needs its own reaction when the menu closes gets its own flag in the `OnOptionValueChanged` and `SaveChangedSettings` wrappers (`gmOptions.ws`; DIFF-09's Ciri option re-levels only while Ciri plays; XP-07's "Disable quest levels" clears or reloads the quest levels, and the group's preset sets the same flag in the `OnPresetApplied` wrapper). Options read at each use (XP-07's experience modifiers) need no flag: the game is paused while the menu is open. A slider value set as a string (`SetVarValue(group, var, "-0.5")`) reads back as that string and is saved so (XP slice X4).

## Build, compile, install

```bash
python tools/build_mod.py --ref <branch> --out build/<area>-<commit>        # the compile-only build: build and compile into a folder
python tools/build_mod.py --install-from build/<area>-<commit> --holder AREA:TOKEN   # install it later, without rebuilding
python tools/build_mod.py --ref <branch> --out <dir> --install --holder AREA:TOKEN   # build and install in one go
python tools/build_mod.py --ref <branch> --out <dir> --install --enable ...          # and add it to mods.settings if missing
python tools/build_mod.py --ref <branch> --out <dir> --release              # without the in-game tests: a build to play or publish
```

- **Required arguments:** `--ref` and `--out` (no default branch or folder: parallel agents must never build `master` or overwrite each other's build by forgetting one). The generators and checks take a required `--worktree` the same way ([Working in parallel](#working-in-parallel)).
- **Installing is the game slot's** ([game-automation.md](game-automation.md#the-game-slot)): `--install` and `--install-from` need the holder's `--holder AREA:TOKEN` and the game closed, and record the build, which `game.py start` checks. Build first, while waiting for the slot; install the prebuilt build when it comes.
- **Commits, not the working tree:** the build takes `<branch>`'s last commit; a warning lists the uncommitted changes under `modGhostMode/` of a worktree that has `<branch>` checked out.
- **The compiler slot:** each `wcc_lite` run (compile, pack, metadata) takes an OS file lock (`%LOCALAPPDATA%\TGM\wcc.lock`), since every run writes REDkit's `wcc.log`, script cache and `temp\` and `editoruser.settings`, and listens on port 37000; a parallel build waits ("waiting for the compiler slot"). Builds and generators run at below-normal CPU priority, to disturb the game's timing-sensitive checks less.

- **Collect:** takes every script `<branch>` adds or changes relative to `vanilla-5.x` into `build/scripts/`, every other game file it adds or changes under `modGhostMode/files/` into `build/files/` (at its depot path), every CSV under `modGhostMode/localization/`, every XML under `modGhostMode/menu/` and every `.bnk` under `modGhostMode/sound/`. Anything else stops the build. `--release` leaves out the test scripts (`modGhostMode/scripts/local/gm/tests/`); the rest of the mod must not call into them.
- **Strings:** the CSVs are merged per language and encoded to `<lang>.w3strings` with `tools/w3strings.py`; an id used twice in one language stops the build.
- **Compile:** runs REDkit's `wcc_lite compilescripts <game scripts> -patch=build/scripts` (about 20 seconds). Errors are printed with file and line; the full log is `build/compile.log`. A failed compile stops the build, so compile errors never reach the game.
- **Pack:** `wcc_lite pack -compression=ZLIB` packs `build/files/` into `blob0.bundle`, and `wcc_lite metadatastore` writes `metadata.store` next to it (logs: `build/pack.log`, `build/metadatastore.log`). **Verified** (pilot slice 3a): the game loads a mod bundle installed this way, and its files replace the vanilla ones.
- **Assemble:** the mod is `build/modGhostMode/content/` with `precompiled.rsblob` (see [How the game loads mod scripts](#how-the-game-loads-mod-scripts)) plus `blob0.bundle`, `metadata.store`, the `<lang>.w3strings` files and `soundspc.cache` (the banks packed by `tools/soundcache.py`; see [Sound banks](#sound-banks)). `--loose` ships the loose scripts instead, for experiments only; `--loose --no-compile` skips the compiler.
- **Install:** copies the mod into `<game>\mods\modGhostMode`, replacing only a folder this script installed earlier, and the menu XML into `<game>\bin\config\r4game\user_config_matrix\pc\` (recorded in the mod folder's `.built-by-build_mod`, so the next install removes stale ones; it never overwrites a file it did not install).
- **Verified** (pilot slices 1–2): the game loads and runs a mod installed this way, with a `[modGhostMode]` entry in `mods.settings`. That mods also load without an entry is from the wiki and not tested.
- **Enable:** mods in `<game>\mods` are enabled by default and load alphabetically. `Documents\The Witcher 3\mods.settings` (`[modName]`, `Enabled=0/1`, `Priority=1..9999`) overrides that. Mod folder names must start with `mod`. Documents may be redirected (e.g. to OneDrive); the script resolves it.

Automated game runs (launch, load a save, run exec functions, quit) are described in [game-automation.md](game-automation.md).

## Testing in game

- **Automated runs:** with the game slot ([game-automation.md](game-automation.md#the-game-slot)), `python tools/game.py run test --holder AREA:TOKEN`, then `python tools/game.py exec "<call>" --holder AREA:TOKEN` and `python tools/game.py quit` launch the game, load the [test save](game-automation.md#test-saves) (saving locked), run exec functions (printing their output) and exit, about 30 s in all, with no key presses. Needs the test-only `modAutomation` and rw3d_cli; see [game-automation.md](game-automation.md).
- **Console:** `DBGConsoleOn=true` in `<game>\bin\config\base\general.ini` (**verified**). A Steam "verify files" may reset it. Open with `~`; Ctrl+V pastes.
- **In-game test functions** live in `modGhostMode/scripts/local/gm/tests/gmTests.ws`: one `exec function gmtest_<feature>()` per feature, reporting `PASS <check>` / `FAIL <check>` lines with `LogChannel('GMTest', ...)`, so `python tools/game.py exec "gmtest_stam01()"` prints the results. Write them so they run without character actions where possible (e.g. add an effect directly instead of casting). Test-only wrappers (probes that log drains, attacks or NPC decisions) belong in `tests/` and do nothing unless `GMTestProbes()` is on: a test that reads their logs switches them on in its reset, or `gmtest_probes(true)` does; off by default, so a test build plays like a normal one.
- **Scripted hits:** build a `W3Action_Attack`, `Init` it and pass it to `theGame.damageMgr.ProcessAction` (as `gmTestsDef.ws` does). Damage added as `DAMAGE_NAME_DIRECT` skips the victim's `ReduceDamage` (parries, Quen, armour rules): use a physical damage type to test anything decided there. The attack name adds the attacker's own, random damage, so measure a reduction inside the step (a test probe around `CActor.ReduceDamage`), not by comparing two hits. To give a scripted hit real weapon damage, pass the attacker's weapon: Geralt's `GetItemFromSlot('r_weapon')`, an NPC's first `GetInventory().GetHeldWeapons()` entry (a monster's teeth or claws are a held `monster_weapon` item; its `r_weapon` slot can be empty). Each step of a hit's damage can be read with the damage probe (`gmtest_dmg()`, `tests/gmTestsDmg.ws`). A melee hit's damage is randomised: `W3Action_Attack.AddDamage` multiplies every damage type of a melee attack by a random 0.9 to 1.1 (vanilla, 1.32 and legacy alike), so a real hit's raw damage differs from the weapon's by up to 10%; compare hit damage with item damage within that margin. `ProcessAction` rolls a crit for a scripted hit by the attacker's crit chance unless `SetCriticalHit()` forced one: read `IsCriticalHit()` afterwards. A hit's attack power is Geralt's attack power plus that of the abilities tagged with the attack's name (`attack_light`, `attack_heavy`: the classic Muscle Memory and Strength Training per level) plus the attack action's own terms; `gmtest_ui01_hits` compares it with the character panel's list. Scripted hits in one call fall within one swing's time, so Strength Training (new tree) treats them as one swing.
- **Test dummy** (`tests/gmTestDummy.ws`): a hostile NPC that stands still and has exact stats, for tests that need a predictable opponent. **Verified** with a bandit, a wolf, a drowner and a wraith: stats read back as set, it neither moves nor attacks, and the damage probe passes against each.
  - `gmtest_dummy("human")` spawns one 2 m in front of Geralt (optional level and distance). The body is any NPC template: the kinds in `GMTestDummyTemplate` (`human`, `wolf`, `drowner`, `ghoul`, `nekker`, `wraith`, `nightwraith`, `endriaga`, `arachas`, `werewolf`, `golem`, `troll`, `bear`) or a template path, so humans and every monster category (Vitality or Essence) are covered.

Settable: armor, the 14 point (bleeding, will and burning points since EFX-08) and 17 percentage resistances, Vitality, Essence, attack power, `damage_final_multiplier` (the difficulty's: DMG-05 multiplies a hostile NPC's final damage on Geralt by it, 2 on Hard since DIFF's slice D1; 5.x multiplies any NPC's raw damage, 2.3 on Hard), `critical_hit_damage_reduction` (1: crits add no damage, so attack power compares exactly). A level-up heals Geralt fully (not on "Death March!"), so a check of the Vitality percentage across a reset records it just before the reset (`gmtest_xp09_prep(0, pct)`). Switch the tree with `autoconfigset(GMGameplayOptions, GMClassicSkillTree, false)` and `gmreset()` in one exec call: the level rule follows the profile the reset sets (SKL-02's facts), not the option alone; `gmtest_xp09_asnew()` turns a loaded classic save's profile into the new tree's (a save from before slice X5). A Place of Power: `gameplay\interactive_objects\places_of_power\place_of_power_quen.w2ent` spawned with `CreateEntity` starts idle, and `GotoState('PlaceOfPower_Activated')` grants its point by its own code (`gmtest_xp09_pop_a/b/c`; the shrine buff removed afterwards).
- **The kill counter on a save without kills** (XP slice X4): UI-10's `gmEnemiesKilledByType` is empty until the first kill sizes it (`GMIncKills`), and the test helper `GMTestKillsAdd` writes nothing into an empty array, silently: a test that sets kill counts first gives a kill (or calls `GMIncKills` and takes it back with `GMTestKillsAdd(type, -1)`, as `gmtest_xp07_start` does). `RoundMath` (5.x's script, `core/math.ws`) rounds halves up (0.5 → 1, 2.5 → 3, 7.5 → 8); pick test values whose products are not halves in float, or work them out with that rule.
- **The experience options in tests** (XP slice X4, `tests/gmTestsXpOpts.ws`): `GMTestSetLevelOverride(n)` (`tests/gmTestsAi06.ws`, a wrapper of `W3PlayerWitcher.GetLevel`) holds Geralt's level for the quest and kill rules while rewards level him up, so many cases can run in one session; `gmtest_xp07_set(k)` with the pause menu open and `game.py resume` change the options through the menu's code path; the options stay as the last case set them (saved in the settings file): set case 0 at the end and restore the settings file with the game closed.
- **Quest rewards in tests** (XP slice X2): `theGame.GetReward('<reward>', r)` reads a reward's experience, level and gold as the game has them; `theGame.GiveReward('<reward>', thePlayer)` gives it through `CR4Game.OnGiveReward` in the same call, so the experience gained is `levelManager.GetPointsTotal(EExperiencePoint)` after less before; the same reward can be given again. `gmtest_xp01()` raises Geralt to each level it tests with exactly the experience the level starts at, so the rewards that follow do not level him up. It changes Geralt (levels, items, crowns): run it from a freshly loaded save and reload or quit without saving; set the mode in its own exec call before it (`gmtest_diff_mode(EDM_Hardcore)`; enum names work as exec arguments). The post-story condition is the fact `witcher3_game_finished` above 1 (5.x's halving), which a test can set and remove (`FactsAdd`, `FactsRemove`). No autosave was written.
- **Giving rewards in tests** (ECON slice E4, `tests/gmTestsEconE4.ws`): the crowns a reward pays are `GetMoney()` after `GiveReward` less before (5.x's `OnGiveReward` adds `gold` × the haggled multiplier, then removes the multiplier); put them back with `RemoveMoney`, remove the items it gave, and take its experience back (`GMTestTakeExp`). A reward with experience can level Geralt up (a level-up asks for an autosave): hold his level at 100 with `GMTestSetLevelOverride` while giving it (a reward with a level then gives the minimum 5 XP; one without a level its own experience) and check he is well short of his next level first. A haggled deal is made through the popup's result function (`DialogueSliderDataPopupResult(value)`: the multiplier is value ÷ the reward's live gold). **Keep reward-giving checks out of `gmtest_regress()`'s frame**: at its end they went with more failures of the panel's AI-18 stone check (below; the link is not proven), so they run in `gmtest_panel()` (after the AI-18 check), the data test in the regression.
- **Who killed it, a Vitality effect at a load, menu events** (XP audit, `tests/gmTestsXpAuditChecks.ws`): a scripted kill credits whoever `W3DamageAction.Initialize` names as the attacker, so `OnDeath`'s `ShouldGiveExp` can be tested with an ally or a guard as the killer (`GMTestXpWhoKill`); a test can take the experience back with a test `@addMethod` on `W3LevelManager` (`points[EExperiencePoint].free -= n`), so such a check can run in the regression. At a load the player's effect manager and abilities come back from the save inside `CActor.OnSpawned` (`abilityManager.Init`, then `effectManager.OnLoad`), before a `W3PlayerWitcher.OnSpawned` wrapper's code runs, so an effect's ability (Blood and Wine's "Well rested", +500 Vitality) is in place there; an ability adding Vitality later keeps Geralt's Vitality percentage. `AddEffectDefault(EET_WellRested, thePlayer, "...")` adds the effect's ability through the base effect's `OnEffectAdded`, without Corvo Bianco's bed. A menu's events can be called from a script on the open menu (`GMTestOpenCharacterMenu()` after `dupemenu()`; `OnGetLockedTooltipData(12)`): to read what an event sends to Flash, route the text through a global function the test wraps (`GMLockedSlotDescription`).
- **Both skill trees:** a check that involves a skill runs once with the classic skill and once with the new tree's counterpart; how to switch the tree in a test is in [game-automation.md](game-automation.md#setting-up-geralt-and-the-world).
- **Crafted hits on Essence users:** an NPC on Essence (monsters, the Wild Hunt, humanoid monsters) takes nothing from physical damage types (slashing, piercing, bludgeoning): give a crafted hit `SilverDamage` (resisted by the physical resistance) or an elemental type; and armor stops every type (DMG-01), so a crafted fire hit must pass the victim's armor to deal fire damage (and call `OnFireHit`). A crafted hit that is not melee (`W3DamageAction.Initialize` with `isM` false) avoids the victim's guard, parries and counters (AI slice C1).
- **Class defaults of entities apply only where the entity file sets no value:** a scope-based `default projDMG = 200.f;` on a projectile class changes nothing for a projectile whose entity stores its own damage (Eredin's frost projectile keeps its entity's 500; AI slice C2). Read an entity's values in game before relying on a class default: spawn it (`theGame.CreateEntity`) and read its fields through a test `@addMethod` getter, in the same call (`GMTest_ai17`).
- **A projectile's collision from a script:** `Init(caster)`, `ToggleActiveState(true)` (5.x, public on `W3AdvancedProjectile`), then call its `OnProjectileCollision(pos, normal, <the victim's CMovingPhysicalAgentComponent>, groups, 0, 0)`: its own damage code runs on that victim, as at a real hit; with a `NULL` component only the base class's part runs (5.x's level term). `GMTestAi17Collide(path, caster, victim)` does this for any projectile entity, with the victim watched by the damage probe (AI-C audit F3). To fly one at Geralt: create it, `Init(caster)` and `ShootProjectileAtPosition(projAngle, projSpeed, target, range)` (`gmtest_ai18_shoot`, AI slice C2).
- **Instant kills in tests:** vanilla's `ForceInstantKill` ability on the attacker makes every hit of it on a non-player an instant kill through `ProcessInstantKill` (real hits with `gmtest_ai17_force(true)`); a scripted `W3DamageAction` with `SetInstantKill()` does the same. Most contract monsters' entities carry 5.x's `InstantKillImmune` ability (mh102's arachas, mh107's fiend, mh301's griffin, the red-plague creature); mq1051's wyvern (`W3MonsterHuntNPC`) does not, so it shows the class rule (AI-17).
- **Entity enum arrays hold raw numbers:** a list such as `CBuffImmunityParam.immunityTo` (the buff immunities `IsImmuneToBuff` reads, an `array<int>`) stores `EEffectType` numbers, and 5.x inserted two effect types at 127 (`EET_Catalyst`, `EET_ConvergenceTheory`), so a 1.32 or legacy number from 127 up names another effect in 5.x (legacy's acid, 134, is 5.x's 136): translate by name (`gen_ai_ent.py`'s `ENUM_ARRAYS`, AI slice C3). Read the result in game with `IsImmuneToBuff` on a spawned entity.
- **Fistfights from a script:** the quest block's start is the two events: `thePlayer.OnStartFistfightMinigame()` and the opponent's `OnStartFistfightMinigame()` (with `SetFistFightParams` first), ended by both `OnEndFistfightMinigame()`; the opponent then fights with fists and Geralt's light attacks are punches (AI slice C3, `gmtest_ai20_start`). A frozen NPC never holds its fists (`IsWeaponHeld('fist')` stays false even after `MountItem(id, true)`): a test of a fist hit uses a fistfighter left unfrozen for a few frames. An ability with a large negative `vitality` multiplier (legacy's `HealthFistFight*`, ×−10) does not make the health negative: the game floors the multiplier and the health is the flat additions.
- **An ability no XML defines cannot be given:** `AddAbility('<name>')` of a name that no definitions file holds leaves `HasAbility` false (5.x's `EredinInvulnerable`, checked in `ReduceDamage`, is such a name, so its immunity never applies; AI slice C1).
- **Ciri in tests** (DIFF slice D3): vanilla's `Ciri()` and `Geralt()` swap the player safely ([game-automation.md](game-automation.md#playing-as-ciri)); `GetWitcherPlayer()` is NULL while Ciri plays, and `CR4Player` fields belong to each player object, so state a test keeps across the swap goes on `CR4Game`. The new player's `OnSpawned` runs before `CR4Game.OnPlayerChanged`; at a save load `OnPlayerChanged` does not run. Her `OnSpawned` gets `spawnData.restored` true at a player change too, not only at a load. **At a load in her sections the NPCs restored with the save are not reached by her spawn's update** (they keep the mode they were saved with; DIFF-09 updates every NPC half a second after her restored spawn). A save made as Ciri into the test-only slot (`gmtest_diff04_lsave_save(key)`) loads as Ciri (DIFF-09); put the slot back as Geralt afterwards. Ciri's `GetLevel()` reads 0, so code that marks an NPC's level bonuses "to recompute" with a player level of 0 skips her sections (AI-01's `SetLevel` writes 0; `GMRecomputeLevelBonuses` uses −2, DIFF audit F2).
- **The boss bar in tests** (DIFF audit F2): `theGame.GetGuiManager().GetHudEventController().RunEvent_BossFocusModule_ShowBossIndicator(true, '<tag>')` (the quest block `ShowBossFightIndicator`'s body) tags the NPC with that tag `HideHealthBarModule` by the next exec call, not in the same call; `(false, '')` hides the bar and removes the tag. The HUD module keeps the NPC it already shows: a contract monster nearby (`W3MonsterHuntNPC`, its own bar when it sees Geralt) takes the bar first, so hide it (or remove the monster) before. The quest function `HealthBarVisiblityQuest(tag, show)` adds the tag when `show` is false; non-latent quest functions can be called from a script and wrapped with a class-less `@wrapMethod` declared as a plain `function` (**verified**; a latent one cannot be called, [Annotations](#annotations)).
- **Journal states in tests** (DIFF slice D3): `GetEntryByString(<uniqueScriptIdentifier>)` finds only entries the save's journal knows (quests reached); for an unreached quest, load its file, `((CJournalResource)LoadResource("gameplay\journal\quests\<file>.journal", true)).GetEntry()`, and set it with `ActivateEntry(entry, JS_Active, false, false)`; afterwards `GetEntryByString` finds it, and `ActivateEntry(entry, <the old status>, false, false)` puts it back (no HUD message, no autosave seen). The identifiers are in the `.journal` files (`startup.bundle`, read with `tools/unbundle.py` and `tools/cr2w_dump.py`).
- **Difficulty in tests** (DIFF slice D1): set a mode with `theGame.SetDifficultyLevel(mode)` and `theGame.OnDifficultyChanged(mode)` (what the menu's confirmation does; `GMTestDiffSetMode`): every NPC's `difficulty_Common*` ability is swapped in the same call, and its maximum health follows. Tests of values that depend on the mode read the multiplier from the game (`health_final_multiplier`'s additive part; `damage_final_multiplier` through `CalculateAttributeValue(npc.GetAttributeValue(...))`, as DMG-05 reads it) rather than a fixed number, so they hold on any mode; set the save's mode back at the end. A mode change rebuilds an NPC's difficulty ability before its re-level timer runs: anything sized for the old mode that adds to `health_final_multiplier` meets the new mode's ability in between (DIFF-04's modifier steps did, until they were taken off in the `OnGameDifficultyChanged` wrapper: from health −100% on "Blood and Broken Bones!" to "Just the Story!" a wolf was left alive with a negative maximum health, DIFF audit F3). `CR4Game.UpdateStatsForDifficultyLevel(mode)` (native per NPC) sets every NPC's difficulty ability and per-enemy variants for the mode passed, not the spawn mode (seen with Ciri's spawn, DIFF slice D3), and **runs no level computation**: anything sized for the old mode (DIFF-04's modifier steps) stays until the NPC's bonuses are recomputed (DIFF-09: a restored bandit held `difficulty_CommonEasy` with "Death March!"'s steps). Only a mode change through the game's path (`SetDifficultyLevel`) re-levels (`OnGameDifficultyChanged`).
- **No mode change inside the regression:** the native `SetDifficultyLevel` alone (without `OnDifficultyChanged`) also rebuilds every NPC's stats for the new mode, even when the mode is set back in the same call: inside `gmtest_regress()` it undid the AI-06 samples' set levels (a drowner set to Geralt + 6 came back at Geralt − 6) and failed three AI-01 checks and the AI-18 stone check in `gmtest_panel()` (**verified**, DIFF slice D4). A check that must run on every mode belongs in its own exec call (`gmtest_diff07(true)`); the regression keeps to the current mode. The one mode-change check in the loop runs last in `gmtest_panel()` (`GMTest_diff04_after`, DIFF audit F4), after every check that reads a regression sample, and sets the mode back.
- **The panel's AI-18 stone check fails intermittently** (a bandit hit by a sorceress's stone shows no knockdown), on about half the fresh launches, more often on a launch's first run. When it is the only failure, run again on a fresh launch and report each run; any other failure, or this one failing on two fresh launches in a row, is a real failure. The stone's damage always arrives; the knockdown is refused at random after `InternalAddEffect`, more often just after another critical effect (ECON audit F5, a fix for AI, open).
- **Run the regression with `god()` off:** `god()` keeps effects such as the stagger off Geralt, so checks that read one on him fail falsely (AI-B audit); a test that needs Geralt alive makes him immortal itself (`SetImmortalityMode(AIM_Immortal, AIC_Default, true)`).
- **Negative effects from a friendly creator are refused** (`W3EffectManager.InternalAddEffect`: creator friendly to the target, not the target itself): the regression's NPCs are friendly to Geralt, so a test that adds a slowdown or expects 5.x's stagger on them uses no creator or sets the NPC neutral (`SetAttitude(thePlayer, AIA_Neutral)`) (AI-B audit F2). The same holds between NPCs: a projectile one of the regression's deserters casts on another deals its damage but applies no effect (they are friends); make Geralt the caster (AI-C audit F3).
- **A spawned NPC's level reads 1 at first:** `GetLevel()` reads the `level` attribute, which the level-bonus timer sets a moment after the spawn; call `RecalcLevel()` to read it in the same call (the HUD's displayed level, `GetExperienceDifferenceLevelName`, needs the NPC hostile to Geralt: set it with `SetAttitude` and back; AI-C audit F6).
- **A state's private function from a test:** a test `@addMethod` on the state (e.g. `W3VehicleCombatManagerStateSwordAttack`) calls it, reached with `mgr.GetState('SwordAttack')` and a cast; fields the state sets in its `OnEnterState` (`rider`) must be set by the test method first (`GMTestHorseDeal`).
- **Horse combat off the horse:** the horse's combat manager exists only while Geralt rides (`GetUserCombatManager()`), but `new W3VehicleCombatManager in theGame` with its `rider` set by a test `@addMethod` (no `Setup`, which registers input listeners) gives the states' functions on foot.
- **A sword drawn by script in `gmtest_regress()` is not always in the hand in `gmtest_panel()`:** a check that needs the weapon in hand (`GetItemFromSlot('r_weapon')`) runs in the regression when one is held and draws only as a fallback (`GMTest_horse`).
- **A behaviour variable set by script does not read back in the same call** (`SetBehaviorVariable('speed', 4)` on Roach, then `GetBehaviorVariable`: 0). A replaced body that needs a value the tests set reads it through a Ghost Mode method a test wrapper answers (`GMTrampleSpeed`); the same for a held key in replaced code (`GMHorseAxiiHeld()` instead of `theInput.IsActionPressed`).
- **A riderless Roach is not hostile to Geralt's enemies,** so her collision rule does nothing; a test wrapper of `W3HorseComponent.GetCurrentUser` makes Geralt her rider for one call (the trampling checks).
- **Item ids are per inventory:** an id from one inventory can name another item in another (Roach's weapon id can be one of Geralt's armor pieces), so code that looks an id up in the wrong inventory reads a random item, not nothing.
- **Regression run** (when a feature is finished; a fresh launch per tree, a few minutes in all), on a build with the tests (without `--release`): `python tools/regress.py --holder AREA:TOKEN --trees both`. Per tree it launches the test save, runs `gmtest_regress()` (`exec --wait 6000`), `ingamemenu()` and `gmtest_panel()` (separate calls), resumes and quits; each tree set explicitly after the load, by `autoconfigset(GMGameplayOptions, GMClassicSkillTree, false)` (new) or `true` (classic) and `gmreset()` in one call (the test save takes its tree from the option at load, and the settings baseline may hold either tree), and the classic tree set back after a new-tree run; `god()` stays off. It prints each tree's counts (`gmtest_regress()`'s SUMMARY line; for `gmtest_panel()` the PASS and FAIL lines after it) and runs a tree once more when only a known flake failed (below). Each area's checks go into its own `tests/gmTests<Area>.ws` (`GMTest_<area>()` in `gmtest_regress()`, `GMTest_<area>_after()` in `gmtest_panel()`), so parallel areas never edit the same list. LOOT's checks roll loot lists into a spawned merchant, which crashes the game after a varying number of rolls, so they are not in the regression: `gmtest_loot()` once, in a launch of its own ([game-automation.md](game-automation.md#setting-up-geralt-and-the-world)). `gmtest_regress()` runs every check that needs no fight, input or menu (each restores what it changes; a check that adds or removes effects on Geralt saves his own effects of those types first and puts them back with their time left: `GMTestEfxSaveBuffs` and `GMTestEfxRestoreBuffs`, `tests/gmTestsEfx.ws`) and logs `SUMMARY regress: N passed, M failed`; the character panel check needs the menu open, so it follows. `gmtest_panel()` also runs the regression checks that must read the game a frame or more after `gmtest_regress()` (an effect's ability counts from the next frame: ITEM-12's resistance gain, `GMTest_item12_after`; an effect's first updates: ALCH's later potion dose, `GMTest_alchport_after`); they report after the SUMMARY line. Long output is cut off by the exec call: read the results from the script log. Add a feature's situation-free checks to `gmtest_regress()` (as a plain `GMTest_<name>()` function) when the feature is finished, except checks that spawn merchants and roll loot into them. Timers that `gmtest_regress()` starts (AI-10's counter window, samples 2.25 and 2.6 s after its call) must fire before `ingamemenu()` pauses the game, and spawns in the regression cost game time, hence `--wait 6000`; when only that check fails ("0 of 2", "1 of 2"), run again with a longer wait. Spawn heavy templates (a quest NPC's) in a `gmtest_panel()` check, where the game is paused.
- **Exec functions** are the quickest probes: `exec function gmsomething() { thePlayer.DisplayHudMessage("..."); }`, then type `gmsomething()` in the console.
- **Script log:** start the game with `-debugscripts` (`tools/game.py` does) to get `LogChannel` output in `Documents\The Witcher 3\scriptslog.txt`, written live and rewritten at each start. **Verified** on 5.0. The console does not show `LogChannel` output; rw3d_cli `exec` prints it.
- **Compile errors at game start** show a "Script Compilation Errors" window with file and line. With a blob they should not happen, since the build compiled it. If one appears, the game and `wcc_lite` disagree; record the case here.
- **A console command that does nothing** usually means the script was not loaded at all (e.g. loose scripts next to a blob), not that it failed.
- **Test save and setup:** load the [test save](game-automation.md#test-saves) (level 1, just past the tutorial) by name, then give Geralt the level, skills, items and enemies a test needs with vanilla exec functions (`setlevel`, `skilleq`, `additem`, `spawn`, ...; see [game-automation.md](game-automation.md#setting-up-geralt-and-the-world)). Read the state back with `modAutomation`'s probes (`autoplayer()`, `autoskills()`, ...): vanilla debug functions log nothing in the release build. Actions that need input (casting, attacking) cannot be triggered from the console yet.
- **Saves:** test with a new game or a dedicated test save. Do not overwrite personal saves with a test build. Legacy Ghost Mode needed `cleardevelop` (console) for existing characters; see [save compatibility](feature-mapping.md#save-compatibility).

## Working in parallel

Areas that share no files can be ported at once, one agent each, sharing the one game install through the game slot ([game-automation.md](game-automation.md#the-game-slot)). This is the procedure an area agent follows; the parent's brief points here.

1. **One worktree per area**, created by the parent: `..\TGM-<area>` on `gm/<area>` (from `master`) holds everything the area changes: the mod code and the generated XML, and its tools and generators, its feature doc, its `attribution.csv` rows and its open questions. Generators, checks and builds run from that worktree with `--worktree .` and `--ref gm/<area>` (both required).
2. **Commit at every testable point** on `gm/<area>`, and make that commit's compile-only build into a folder named for it: `python tools\build_mod.py --ref gm/<area> --out build\<area>-<short commit>`. Before asking for the game: `python tools\gen_all.py --worktree . --verify` passes, and so do `deviations.py --check` and the build's compile. The commits are squashed into one per slice at integration, and `gm/<area>` is merged into `master`.
3. **Game-slot commands run from the main checkout's tools**, `..\TriangleGhostMode\tools\` (the only copy with rw3d_cli and the gating): `game_lock.py`, `game.py`, `regress.py` and `build_mod.py --install-from`.
4. **Ask for the game:** `python ..\TriangleGhostMode\tools\game_lock.py request --who <area> --why "<slice>: <checks>"`. Exit 0: granted, the token is printed. Exit 2: queued; then `game_lock.py wait --who <area>`: in the background when there is other work (you are notified when it exits), or in the foreground with `--timeout 540`, again on exit 2, when idle. Exit 3: paused, or your token was revoked: stop game work and tell the parent. Claim the grant with a game command within the claim deadline (5 minutes unless `status` says otherwise), or it passes to the next agent.
5. **The turn**, every command with `--holder <area>:<token>`:
   1. install the last testable build: `build_mod.py --install-from ..\TGM-<area>\build\<area>-<commit>` (never rebuild while holding the game);
   2. `game.py run test` (only the allowed saves, [game-automation.md](game-automation.md#test-saves); saving is locked automatically), then the slice's checks with `game.py exec`, in both trees, plus the "fail first" throwaway build when one is needed; keep each exec short, so a pause reaches you quickly;
   3. `regress.py --trees both` when the regression is due;
   4. `game.py quit`, then `game_lock.py release`; report what the release prints about the saves.
   While queued or holding the game, never run a long command in the foreground: a foreground command blocks the agent, so the grant notice only reaches it when the command ends. Anything over about a minute (`gen_all.py`, `--verify`, a build) runs in the background while queued; check the wait's result between steps.
   **Integration: never discard a regeneration's output unchecked.** After `gen_all.py` on the integrated branch, read `git diff --stat --ignore-cr-at-eol`: files that differ only in line endings can be restored, any other change is real and gets committed (a real change discarded as line endings once left two abilities defined twice).
6. **Release before editing code.** If a check fails: quit, release, fix, commit, build, then ask again. Uncommitted edits stay where they are; the build takes commits only.
7. **Docs:** findings for `development.md`, `game-5.0-changes.md` or `tools.md` go into a "For the shared docs" block in the area's feature doc; integration moves them. Until the slice is integrated, the area's docs say "verified on the area build", and regression counts are given as "+N checks".
8. **Shared files:** settle before branching which area owns a file several areas need (one `@replaceMethod` per function in the whole mod), and give areas their own lines where they must add to one list (per-area test files, `item_layer.py`'s per-area sets); the string CSVs merge by union (`.gitattributes`), and the build stops on a duplicate string id.
9. **Integration** (a fresh integrator agent, in batches): merge the squashed `gm/<area>` into `master`; rebuild generated files with the merged tools (`gen_all.py`, taking either side of a conflict first); run every `--verify`, `check_modsigns.py`, `dlc_conflicts.py`, `deviations.py --check` and a compile; regenerate `deviations.md` and `coverage.md`; run the integrated regression in both trees as holder `integration`. A dependency is integrated at once; an audit follows an integrated regression; area agents rebase at their next slice boundary, never inside a slice.
10. **Git:** never fetch; push only `gm/<area>`; no `git gc` (`gc.auto` is 0 while parallel work runs).
11. **Never** (they bypass the lock): call `rw3d_cli` directly, install with `--scripts`, copy saves by hand, edit the settings files, pass `--parent`. The hard rules still hold: scripted checks only, only the allowed test saves, never save over the owner's saves, no story teleports or time skips.

- [Skill Tree Reforged](https://github.com/invaliduser231/SkillTreeReforged) (MIT): a 5.0 mod built from annotations that shows the pre-5.0 skill tree in the new character menu and gates skills by tier; what the port can take from it is in [skl.md](features/skl.md#skl-02-skill-tree-option).
- [modSaveNames](https://github.com/MajaAgent/modSaveNames): a small 5.0 script mod built only from annotations, verified in game by its author. Useful syntax examples.
